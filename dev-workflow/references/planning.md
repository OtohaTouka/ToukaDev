# 規劃程序（步驟 1–3）

準備實作計畫時讀取。以下 `references/` 路徑以本 Skill 根目錄為基準。

## 步驟1｜恢復必要狀態

接續工作或實作時，依 SKILL「適用性與按需程序」的順序讀有效 current 與任務精確連結，
不依日期猜最新、不遍讀歷史；當次對話已明確的目標、成功條件與範圍直接沿用，不重問。

## 步驟2｜讀取對應正本

已知正本直達必要章節，未知先查導航再作有範圍的搜尋，遇到架構決策才讀相應 ADR；
文件衝突或來源不清楚時立即提出，不自行選答案。

## 步驟3｜需求確認 + 撰寫實作計畫

主代理代審（預設）時，主代理保留人類已確認的目標與驗收條件，將調查及方案撰寫交給執行者，
再依原始需求審核；主代理自己寫的內容交新上下文的 reviewer。計畫整理成一頁白話版，經非作者的
reviewer 審過後請人類核准，核准即為本任務的委託。已清楚的需求不重問；技術方案與範圍內修正由
主代理處理，只有無法由現有證據決定的需求取捨或範圍變更回人類。完整程序見 `references/supervisor-delegation.md`。


### 3-0. 需求釐清（新增）

**在寫實作計畫之前，AI 必須先確認需求足夠清楚。**

收到任務描述後，AI 先自我檢查：

```
□ 我知道這個功能做完，使用者可以做到什麼事嗎？
□ 我知道成功的條件是什麼嗎？
□ 我知道邊界在哪裡嗎（哪些不在這次範圍內）？
```

**三個都能回答 → 直接進入 3-1。**

**有任何一個不確定 → 用 Gherkin 格式引導使用者確認：**

AI 把理解到的功能翻譯成 Gherkin 場景，呈現給使用者：

```
我把你說的需求理解成這樣，請確認對不對：

場景：[功能名稱]

  Given [使用者目前的狀態或前提條件]
  When  [使用者做了什麼動作]
  Then  [預期看到的結果]

有沒有哪裡不對，或是漏掉的情況？
```

**Gherkin 確認規則：**
- 一次呈現一個場景，等使用者確認或修正
- 使用者修正後，AI 更新場景再次確認
- 若有多個主要情境（例如成功、失敗、邊界情況），逐一列出
- 全部確認完才進入 3-1

**Gherkin 撰寫原則（給 AI）：**
- Given：使用者的起始狀態，避免技術細節
- When：使用者做的動作，用動詞開頭
- Then：使用者看到的結果，不是系統內部的狀態
- 用繁體中文撰寫，不要用英文

**範例（記帳功能）：**

```
場景：新增一筆支出

  Given 我已登入，目前在主頁面
  When  我輸入「晚餐 350 元」並按下新增
  Then  我應該看到這筆記錄出現在列表最上方
   且  我的本月支出總額應該增加 350 元

這樣對嗎？有沒有漏掉的情況，例如輸入格式錯誤的時候？
```

### 3-1. 問題理解

需求已清楚或必要 Gherkin 確認完成後，整理：
- 根本需求是什麼？
- 影響範圍：哪些模組、哪些介面？
- 本次範圍內的場景清單（已明確需求或 3-0 確認的 Gherkin）
- 本次明確不做的事項

### 3-2. 方案設計

- 擬採用的實作方式
- 依下表逐項說明 SOLID 的適用性、設計證據或不適用理由
- SSOT 影響：哪個文件需要更新？
- ADR 影響：是否需要新增 ADR？計畫要在程式、測試或文件引用新的編號或登記（ADR、豁免、守衛基準）時，寫明在哪個單位建立，排在第一個引用它的單位之前或同一單位；其他少一半就會讓檢查失敗的成對改動（例如刪檔與它的連結、改檔與讀它的既有測試）放在同一個單位，每個單位交件時檢查都要綠。

SOLID 逐項回答適用性與證據或不適用理由；不為湊項目新增無需求的 class、繼承、interface 或 Registry。
共同工程原則以適用 AGENTS 的共同基線為準；依語言、範式與當次變更作設計判斷。

| 原則 | 本次需回答的設計問題 |
|---|---|
| S：單一職責 | 函式、模組或元件是否責任清楚，有一致的修改原因？ |
| O：開放封閉 | 已知擴充點能否透過組合、設定或適當抽象擴充？不等於永遠不能改既有程式。 |
| L：里氏替換 | 有替換關係時，輸入、輸出、錯誤與行為契約是否一致？沒有相關關係時說明不適用。 |
| I：介面隔離 | 呼叫方是否被迫依賴不需要的能力？函式與模組邊界也可提供合適介面。 |
| D：依賴反轉 | 高層業務是否透過穩定契約使用外部能力？傳入函式或抽象介面皆可依範式採用。 |

不得用不適用掩蓋必要分責、耦合或替換契約違反。SOLID 是設計審查；lint、測試與有限文字
守衛只能提供部分證據，不證明任意程式已完整符合五項原則。SSOT 管理同一概念的正本，
DRY 不要求合併偶然相似但責任不同的程式。

### 3-3. TDD 測試計畫

**直接從 Gherkin 場景轉換為測試描述：**

```
場景（來自 3-0）               對應測試
────────────────────────────────────────────
Given/When/Then 場景1    →    test_新增支出_應出現在列表頂部
Given/When/Then 場景2    →    test_新增支出_應更新月支出總額
Given/When/Then 失敗場景  →    test_新增支出_格式錯誤_應顯示提示
```

- 測試工具：Python → pytest；JS/TS → Jest 或 Vitest
- 預期失敗原因（紅燈理由）
- 專案 AGENTS 的「技術棧與執行命令」是實際命令正本，引用既有 package／工具配置；spec 記品質需求與驗收項目，不複製另一套命令。
- Python／JS／TS 是目前既有工具流程；其他語言先揭露模板、測試、lint、型別與安全掃描缺口，補齊本專案必要驗證方式才承諾完成，不宣稱全面支援。

### 3-4. 風險與注意事項

- 潛在副作用、邊界情況
- Docker 依賴或環境風險
- 規模估計與停止線：計畫附產品程式與規則文件的行數估計（給範圍，以最不樂觀的一端為準）；實作後這部分的淨增減比估計多出 100 行以上，且估計為增加時超過 1.5 倍，開 PR 前停下問人類。
  估計與實際都用 git 淨增行（新增減刪除，含空白、註解與說明）；估計要算進審查常要求的保護（錯誤處理、邊界檢查），並參考同類任務的實際數字。實際超過或預計會超過上一句的停止線時照實停下回報，不得用降低品質的方式壓行數（拿掉型別、合併或刪測試、先寫後測、刪說明）；驗收的一方收到這種交件要退回。
  測試不計入停止線，改在步驟12的變更摘要附兩項證據：改到的產品程式被測試執行到的比例（專案有宣告覆蓋率命令時；沒有就寫未量測），以及釘住既有行為的測試在故意改壞後會變紅的紀錄；兩項都沒有的測試刪除或寫明理由，變更摘要另列測試行數。改進任務的停止線另依 improvement-run.md。
  故意改壞後的紅要對得上被改壞的地方（看失敗訊息），基準與改壞在同樣的環境條件下跑。
- 執行中可能要人類決定或會被檢查擋下的點：範圍外的檔案（含會讀到被改檔案的既有測試與檢查程式：在測試與檢查程式（守衛）所在的資料夾用 `git grep` 查被改檔案的路徑與模組名，
  以及要改的函式、常數、錯誤碼、端點或命令列字串；行為改變時，再從呼叫被改函式或端點的測試挑出依賴舊行為的；查到的列進該單位的檔案清單）、受保護的規則、宿主的安全分類器（例如要 AI 寫繞過或逃逸測試、或擔任找繞過的審查者；計畫先列被擋時的替代證明，例如只讀設定值、fail-closed、當成能繞過來防）、外部服務實測需要的設定或金鑰位置（只確認存在，不讀內容）、行數停止線的數值；
  能先查的先查（受保護位置依專案資料保護規則，不能查就列給人類確認），要決定的附建議列進一頁計畫一次問；人類核准的預設做法，執行中照做並事後回報，
  但每批外部實測、對抗式或多代理複審、資料外傳、不在委託內的 commit、不可逆動作、受保護規則的移除或弱化、停止線觸發時的停下，以及專案要求更嚴格的逐次同意，一律不套用預設做法，仍逐次取得同意（一頁計畫中單獨明列並經人類同意的那一項，依原同意範圍執行，不算預設做法；停止線觸發時的停下除外）。
  已核准的實測命令改了寫法（加引號、換 shell、包裝）後，開跑前先用不送請求的方式核對實際收到的參數。

## 步驟3-6. 安全性自動檢查

**實作計畫完成後，AI 必須對照以下清單，確認本次任務是否觸發安全風險。**

不需要使用者提問，AI 主動執行，有觸發就說明，沒有觸發簡短帶過即可。

---

> 📋 **安全性檢查清單**：5 類風險（身份/密碼、前端儲存、資料庫查詢、API 端點、敏感資料與版控）的觸發條件、❌/✅ 判準、安全提醒文案與輸出格式，見 `references/security-checklist.md`。AI 逐項對照本次 Gherkin 與實作計畫；**有觸發就必須在實作計畫裡用安全方式處理（不是建議）**，並於審核點 DEV-A 一併確認。
