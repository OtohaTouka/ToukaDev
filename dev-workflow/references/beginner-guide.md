# dev-workflow 新手導覽

> 從 SKILL.md 移入。標準模式下 AI 讀取本檔；精簡輸出模式跳過。

完整規則由已安裝 dev-workflow Skill 的 `references/review-protocol.md` 定義。

## 這個 Skill 在做什麼？

這是你完成初始化之後，每次要加新功能或修 bug 時都會走的流程。
流程強制「先想清楚再動手」，避免 AI 寫了一堆你不要的東西。

精簡輸出模式只會縮短說明；文件快速路徑只處理純文件或 typo，兩者都不會取消必要授權。

**你需要做什麼：**
- 描述你想加的功能或遇到的問題
- 看主代理整理的一頁白話計畫並點頭：預設由主代理代審，核准計畫就是委託主代理在範圍內派工、審核與驗收
- 寫的人和審的人不能是同一個：其他 AI 寫的成果由主代理審，主代理自己寫的內容交給另一個新的 AI reviewer；你隨時可以改用其他審核方式
- 計畫會寫明是否包含存檔（commit）、合併進共用分支或推上遠端；只有主代理代審且在你核准的計畫範圍內，才能在完成後審核（DEV-B）前先存檔到工作分支，其他審核方式的 commit 仍要等 DEV-B 通過並取得授權；`AI_DELEGATED` 仍須純 PASS

**AI 會自動做什麼：**
- 寫測試、寫程式碼、跑測試、檢查品質、更新文件並準備 commit
- 只有 DEV-B 通過且取得對應授權後，才會把成果合併或提交進共用分支
- 在審核點整理白話摘要與技術證據，不要求你自己讀懂程式碼
- 在本機進度紀錄更新工作清單與審核結果，轉成網頁並告訴你檔案位置，你不用開口問也看得到進度（見下方「怎麼看進度」）
- 任務結束時清掉自己建立的暫存，或寫明保留理由（見下方「暫存怎麼清」）

**五種審核方式：**

1. 人類自行審核
2. 委託一個獨立 AI 技術審核
3. 人類＋一個 AI reviewer（無法證明嚴格獨立時只算參考意見）
4. 對抗式多代理複審（額度消耗極高，必須由你明確同意）
5. 主代理代審（`SUPERVISOR_DELEGATED`，預設）：你核准一頁白話計畫後，由主代理一路派工、審核與驗收

第 5 種是預設，適合「你只跟主代理討論，主代理指揮多個 AI 做事」的情況。主代理先把你要決定的事（目標、範圍、
每一項對你有什麼用、風險、完成條件、誰來做與 Git 操作）整理成一頁白話計畫，每項一兩句，以 40 行內為目標；
審核經過與技術細節你問才說。計畫交給另一個 AI reviewer 審過，再請你核准；你核准就等於委託。
之後主代理負責派工、找問題、退回修正及整體驗收，其他執行者寫方案、程式、測試與文件。
同時有多個 AI 改檔案時，各自用自己的工作資料夾，不會互相改到。可用子代理、其他對話、CLI 實例或
等效方式，不要求新增框架。
只有命中觸發清單時，主代理才會在一頁計畫中把對抗式多代理複審單獨列成選項，寫清楚人數、角色與額度；你單獨選它才算同意。
有效委託內不逐關再問你；需求超出範圍、必要權限不足或無法收斂時才請你決定，最後統一回報。
這種結果叫 `SUPERVISOR_ACCEPTANCE`，不是嚴格獨立 reviewer，也不是把參考意見直接改成通過。
必要測試與審核對象仍要核對。詳細程序見 [主代理代審程序](supervisor-delegation.md)。
其他四種方式在你要求改選，或工具沒有辦法派工時才會列出；工具沒辦法派工時會建議第 3 種。

高風險工作只有命中具體條件才會建議多代理；關鍵風險會強烈建議一次。AI 絕不會未經你
同意自行啟動，也不會在你拒絕後沒有新理由地一直詢問。

如果 reviewer 會把內容送到其他 AI 服務或 premium 模型，AI 必須先告訴你送什麼、送去哪、
對方有沒有資料保證，取得你明確同意；說不清楚對方條件時就不能傳送。
工具無法保證 reviewer 全新、唯讀且不能再叫其他 agent 時，也不能把它標成合格的獨立 reviewer。

原四種模式的 AI reviewer 如果無法確認實際用了哪個模型，AI 必須說明；這時結論最高只能是
`PASS_WITH_NOTES`，不能滿足 `AI_DELEGATED` 的自動繼續或 commit。
主代理代審不以 actual model 或 effective sandbox 的 runtime attestation 作入口門檻，也不聲稱
已有這些證明；完成任務所需的測試、來源與其他技術證據仍不可省略。

`AGENTS.md`、交班文件或平台 Memory 可以幫新對話記得長期規則與偏好，但不能代表你已同意
這一次的審核模式、資料傳輸、多代理、實作或 commit。舊模式依各次審核確認；主代理模式可核對
原始人類委託後續接同一任務，換執行者或等效工具不重問，另一份計畫不能沿用。

DEV-B 審核時會記下 git 的編號，代表這次要合併的全部內容，包含一般 diff 看不到的新檔，以及其他對話在同一分支留下的改動。
內容一變編號就不同，必須回到 DEV-B 重審，不能把未審內容合併或提交進共用分支。
主代理模式的重審仍交主代理，無須因此重問你。

**完成後的樣子：** 一個新功能（或修好的 bug），附帶測試和更新過的文件。主代理代審時，成果可能已在你核准的
計畫範圍內先存檔到工作分支；要合併或提交進共用分支，必須 DEV-B 通過並取得授權，否則交付候選並明示未合併、未提交。

**看到看不懂的詞？** 查閱專案內的 `docs/glossary.md`（project-init 初始化時建立），或框架的 [glossary.md](../../glossary.md)（依安裝指令複製到 skills 目錄）。

## 怎麼看進度

主代理代審時，主代理開始就會告訴你進度紀錄和網頁的完整路徑。找到 `.toukadev/progress/index.html`，
雙擊就會用瀏覽器打開，不用網路，也不用另外裝程式。macOS 的 Finder 預設看不到 `.toukadev` 這種開頭是點的
資料夾，可按 Command＋Shift＋句點顯示，或直接用主代理給的完整路徑。

- `index.html` 是總覽，每個任務一列，最近改過紀錄的排在最上面；單一任務的網頁在同一個資料夾，檔名是任務代號加 `.html`。
  在總覽點任務名稱就能打開詳細頁，詳細頁上方的「回總覽」可以回到總覽。
- 最上面是「需要你決定的事」，有內容時會醒目標示。
- 工作清單顯示誰在做、誰在審，顏色代表狀態。執行者做的東西，主代理驗收後才打 ✔；審核和你的決定這類步驟，
  做完只標「完成」。
- 右上角的「畫面更新於 幾點幾分幾秒」每 5 秒會跳一次，代表網頁還在自己更新。
- 有些工具（例如 Claude 桌面版的內建瀏覽器）只把本機檔案顯示成快照，不會自動更新；這時右上角會改寫
  「此畫面不會自動更新：請用一般瀏覽器開啟 index.html」。要看即時進度，就用 Edge、Chrome、Safari
  這類一般瀏覽器打開 `index.html`。
- 選取文字時網頁會暫停更新，下方會寫出原因；取消選取就恢復。
- 右上角的「主題」按鈕可以輪流切換跟隨系統、淺色、深色，選擇只記在這個瀏覽器。
- 網頁也寫「紀錄最後更新：幾點幾分（幾分鐘前）」，看的是紀錄本身多久沒改。任務進行中
  超過 30 分鐘沒更新會變黃、超過 2 小時
  變紅，寫「可能還在做，也可能忘了更新」；在等你決定時改顯示「等你決定」，不變色。網頁分不出 AI 是在長時間
  工作還是忘了更新，想確定就直接問主代理。
- 看到「格式警告」，代表紀錄少了一整段、狀態寫了規定以外的字（例如打錯字），或進行中任務的審核時間比上一列早、比紀錄存檔時間晚（多半是估的）；內容照樣顯示，不會悄悄消失。
- 網頁只是同一份文字紀錄比較好看的版本。程式跑不起來時主代理會告訴你，直接打開同名的 `.md` 也看得懂。
- 資料夾裡如果有舊版程式產生、或不是這支程式產生的同名網頁，新版不會覆寫它；主代理會問你要不要刪掉。

## 暫存怎麼清

AI 做事時會建立工作資料夾、分支和暫存檔。以前這些東西沒人清，會越堆越多，所以現在的規則是：

- 暫存檔一律放 `.toukadev/tmp/<任務代號>/`。這裡的暫存檔是 AI 自己建立的檔案，例如腳本、log、測試用的 repo；
  工具和測試自己的快取照專案原本的設定放，不會為了這條規則搬家。工作資料夾、分支、暫存資料夾一建立就記在
  進度紀錄的「暫存項目」，網頁會顯示還有幾項沒清。
- AI 自己能刪的只有四種，而且只能用不會誤傷的安全刪法；本機的三種，刪之前要先用 dev-workflow 附的
  檢查程式確認（它只檢查、不刪除）：
  1. 這個任務自己建立的暫存資料夾。Windows 會把 git 的檔案設成唯讀，所以規定的刪法會把資料夾裡真的被設成
     唯讀的一般檔案取消唯讀再刪；捷徑、連結、跟別處共用同一份內容的檔案（硬連結），以及資料夾外面的東西
     一律不碰，遇到其他問題照樣停下來問你；
  2. 這個任務的 AI 自己用 git 建立的工作資料夾。git 的刪除指令會連被忽略的檔案（例如 `.env`、`data/`）
     一起刪，還可能順著捷徑刪到資料夾外面，所以檢查程式會先確認：分支正確、沒有改動、被忽略的只有
     能重建的快取，而且除了 Linux／macOS 快取裡本來就有的捷徑以外，沒有其他捷徑（Windows 上的捷徑一律不行）；
  3. 這個任務建立的本機分支；
  4. 這個任務推上 GitHub、PR 已經合併，而且合併後沒有新改動的分支；刪除時 GitHub 會再比對一次，
     內容一樣才刪。
- 檢查程式說可以，AI 才刪；說不行，就問你。
- dev、main 這類共用分支和預設分支，在本機和 GitHub 上都永遠不刪。
- 任務結束時，每一項都要清掉或寫明為什麼保留，清完才算完成。要留的證據會先寫進回報，再清檔案。

**你什麼時候會被問：**

- 要刪的東西不在上面四種裡，例如類型是「其他」的項目；
- 條件不確定或不符合，例如分支在 PR 合併後又有新的改動，或暫存資料夾裡還有工作資料夾；
- 檢查程式沒通過或跑不起來，例如工作資料夾裡還有沒存檔的改動、有不允許的捷徑，或被忽略的檔案不只是快取；
- 刪除指令失敗，例如分支還沒合併；
- 工具自己的東西（例如 Codex 的對話紀錄、它自己建立的工作資料夾、套件快取）：AI 不會刪，只在收尾時告訴你
  在哪裡、多大，由你決定。

這些事不會讓工作停下，收尾時一次列給你；你沒回覆的就不刪。

## 何時讀文件

指定文件的問答可直接讀；接續工作才從 HANDOVER.md 恢復狀態。長程序依目前階段展開。
沒有狀態變化不用寫新交班；已知需求不重問。這不減少測試、安全、審核或當次授權。

## 新手審核版模板（步驟12 使用）

標準模式下，AI 在輸出技術版變更摘要之後，依此模板補一份白話摘要；主代理模式在最後回報或
需要你處理例外時使用，不要求每個內部審核點再次詢問：

**不懂程式碼的使用者看這裡：**

```
✅ 這次做了什麼：[用功能描述，例如「登入頁面現在會顯示正確的錯誤提示了」]

🧪 測試：全部通過（共 [N] 個）

📄 有沒有改到共用設定？[沒有 ／ 有，改了「[是什麼]」]

🏗️ 有沒有做重大架構決定？[沒有 ／ 有，決定了「[是什麼]」，因為「[一句話原因]」]

⚠️ 還有沒有解決的問題？[沒有 ／ 有：[描述]]

🔎 審核方式與結果：[人類 ／ 獨立 reviewer ／ AI 參考意見 ／ 主代理 SUPERVISOR_ACCEPTANCE]；[結果及未解問題]

➡️ 現在能不能繼續？[可以 ／ 需要先修改 ／ 需要你決定]

🙋 需要你決定的事：[無 ／ 超出委託或無法收斂的具體事項]
```

**你的責任：** 確認功能是否符合期待，以及是否接受成本、風險或不可逆行動。
程式碼、測試與架構細節可以交給獨立 AI reviewer；有任何看不懂的地方直接問，不需要假裝懂程式碼。
