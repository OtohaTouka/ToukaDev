# 除錯升級流程（Debug Escalation）

## 核心原則

- **迴圈定義**：AI 重複執行相同動作（相同修復方向、相同指令、相同錯誤出現）達三次，即判定為陷入迴圈。
- **立即停止**：偵測到迴圈後，禁止第四次嘗試，立即進入此流程。
- **誠實交班**：當前模型必須如實記錄所有失敗嘗試，不得美化或省略。
- **強制分析**：接手分析的角色第一件事是分析根本原因，禁止直接跳入修復。
- **一次性使用**：解完即回來源流程的精確中斷點；dev 回原 dev 步驟，初始化回 project-init，不循環使用本流程。
- **有限重試**：同一未解問題回到步驟4的重新分析預設以 2 輪為限，主代理模式可依初始委託明訂其他合理上限；更名或換執行者不清零。無新證據或達上限仍未解決即回報人類，不得無限循環。

---

## 按需程序

- 新事故建立與交棒時，必讀 [程序](references/incident-handoff.md)。
- 沿指定事故接手分析與修復時，必讀 [程序](references/root-cause-recovery.md)。

主代理代審只在有效委託內接續；需要時讀取已安裝 dev-workflow 的 supervisor-delegation.md 程序。
必要 sibling Skill 依本次環境的 catalog／locator 解析實際安裝根；缺少來源時回報具體缺口，
不自行安裝，不要求下游專案存在 ToukaDev repo。初始化事故只讀來源 project-init 的適用
階段與必要主代理程序，不把原四種 reviewer profiles 當作普通派工的前置。

只在真正除錯迴圈、主代理程序判定不收斂，或人類明確要求升級時啟動；純文件問答或正常 TDD RED 不因關鍵字而升級。
全部適用父子規則仍有效；新事故唯一識別與原 FAIL 證據保留，current 只放摘要與精確連結。
接手須完成錯誤、失敗嘗試、程式邏輯、環境依賴、SSOT／介面的五維根因分析，禁止直接修復。
事故來源記 workflow 與精確步驟，例如 project-init 步驟 6、8 或 10-7；有 AGENTS／HANDOVER
不代表初始化已完成。早期尚未建立的 tests／lint／guards 列待驗與補驗步驟，不標 PASS；
必須在來源流程最終驗收前補齊。已建立且適用的驗證仍必跑，不因缺工具而提前做後段骨架。

## 精簡輸出模式（熟練用戶）

依當次偏好輸出結果與下一步；精簡輸出模式不省略五維分析、交班證據、修復計畫或審核。
需要新手說明才讀 README.md；操作與完整格式在對應程序，不強制先讀所有教學。

## 迴圈偵測規則

AI 必須在每次修復嘗試後自我檢查：

```
修復嘗試計數器：[1] [2] [3]

主要觸發條件（符合即觸發）：
□ 相同的錯誤訊息出現3次以上（最明確的迴圈信號）

輔助觸發條件（三項中符合兩項以上即觸發）：
□ 連續三次執行相同或幾乎相同的指令
□ 連續三次修改相同的檔案但問題未解決
□ 連續三次的「解法」邏輯相同，只是換了寫法
```

**觸發時立即輸出：**
> 「⚠️ 偵測到除錯迴圈（相同錯誤訊息第3次出現）。停止嘗試，啟動 debug-escalation 流程。」

## ⏸ 操作點 DBG-OP｜交棒分析

`SUPERVISOR_DELEGATED`：主代理把原事故與中斷點交給新的分析上下文，可用子代理、其他對話、
CLI 實例或等效方式；可選更合適模型，也可如實使用同模型新上下文。主代理只派工與審核，
不代寫根因或修復方案。有效委託內直接續行；缺乏可用調度方式或需要未授權操作才返回人類。

其他模式維持人類操作：

```
此處需要人類手動操作：
- 開啟新 session
- 切換到高階模型（你的工具當下最高階的選項；名詞說明見 glossary「高階模型」）
- 讓新模型讀取除錯交班文件
- 告知新模型從步驟3繼續

💡 若你的工具支援 session 內切換模型（如 Claude Code 的 /model 指令），也可以原地切換；
   但「開新對話」本身有獨立的價值——乾淨的上下文有助於跳出前一個模型的思考死角，
   預設仍建議開新 session。
```

---

## ⏸ 審核點 DBG-A｜確認修復計畫

`SUPERVISOR_DELEGATED`：主代理審閱五維分析、根因證據與修復計畫；必要證據不足就退回分析，
接受後由執行者以 TDD 修復並返回原中斷點，結論為 `SUPERVISOR_ACCEPTANCE`。有效委託內不再問
人類相同審核或開始修復的同意；超出委託或無法收斂才回報。其他模式維持下列人類審核：

```
暫停執行。
輸出：「根本原因分析與修復計畫已完成，請審核後確認可以開始執行修復。」
等待人類確認後才繼續步驟6。
若人類要求修改，回到步驟4重新分析。
```

## AI 禁止行為清單

- ❌ 偵測到迴圈後繼續第四次相同方向的嘗試
- ❌ 分析角色在步驟4完成前提出任何修復建議
- ❌ 省略或美化除錯交班文件的失敗記錄
- ❌ 修復計畫與前三次方向相同（除非步驟4有明確新理由）
- ❌ 修復後測試失敗時繼續往下走
- ❌ 在此流程內部再次觸發本流程（只用一次）
- ❌ 回到步驟4重新分析達適用上限仍未解決後繼續自行嘗試修復，或用換人、更名清零失敗歷史
- ❌ 在本流程內執行 git commit（dev 修復納入原 DEV-B；初始化修復納入骨架驗收，均由來源流程依 Git 授權交付）
- ❌ 解完後未明確宣告來源流程與精確中斷點，或把初始化事故提前交棒 dev-workflow
