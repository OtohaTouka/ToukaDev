# 根因分析與恢復（步驟 3–10）

沿指定事故接手時讀取，先分析再寫修復計畫。
只接手使用者指定或 current 精確連結的事故；多個候選須選擇，不按日期猜測或全文掃描歷史。
歷史 PASS 與同意不是當次修復授權；先完成五維分析與 DBG-A，再以 TDD 修復。

主代理代審（預設）時，先核對本次委託及可核對的原始來源；有效範圍內由主代理
代審 DBG-A，分析與修復均由執行者完成。以下分析角色在其他模式由高階模型接手，在主代理模式
由新的分析上下文接手，可如實使用同模型；不要求特定模型或 runtime attestation 才能分析。

## 來源流程與階段工具

修復完成後回來源流程的精確中斷點；project-init 事故回原初始化步驟，dev-workflow 事故回原 dev 步驟與 DEV-B。
驗證能力分為已適用且已建立、依序尚待建立、依核准技術棧不適用；尚待建立不是 PASS 或永久豁免。

先核對原始委託、核准規格、初始化狀態及精確步驟，不以 AGENTS／HANDOVER 的存在推定
已完成。已適用且已建立的驗證必須執行，失敗或遺漏不得驗收。正常順序尚待建立的能力
以當前可用的最小重現及必要檢查驗證修復，保留原 FAIL，列補驗責任與後續步驟；依核准
技術棧不適用者列理由，不能改寫已宣告必跑項。早期尚無 tests／guards 不可硬跑不存在
工具、宣稱全部通過，或為符合後段命令而提前完成不相干骨架。

以下步驟 6–8 依此三態展開；正常依序尚待建立者可在當前重現已解、必要檢查通過且有
明確補驗安排後返回原步驟，不表示初始化完成。來源流程最終骨架驗收前必須收斂全部
適用待驗項；所需工具仍不可用或證據缺失時保持未完成。專案宣告命令優先於下列示例。

## 步驟3｜分析角色：讀取除錯交班文件

分析角色接手後，依序讀取：
1. 當次指定或 current 精確連結的唯一事故文件，以及全部適用的父子 AGENTS.md
2. 相關檔案清單中的所有檔案
3. 相關測試檔案

初始化早期只讀已建立且相關的檔案，核對缺少能力的階段理由；無適用 AGENTS 或
HANDOVER 時沿原始委託及已可用規格，不自行補造。來源或中斷點缺失時先定位缺口。

讀取完成後確認：
> 「已讀取除錯交班文件。問題摘要：[一句話]。失敗嘗試：[依原始紀錄摘要，不把重試當成不同方向]。我將先完成根本原因分析再提出修復計畫。」

⚠️ 禁止在步驟4完成前提出任何修復建議。

---

## 步驟4｜分析角色：強制根本原因分析


**這是此流程最關鍵的步驟。禁止跳過。**

依序完成以下分析：

### 4a. 錯誤訊息解讀
- 錯誤訊息的每一行代表什麼？
- Stack trace 指向哪個確切位置？
- 這個錯誤在此語言/框架中通常代表什麼？

### 4b. 失敗嘗試的模式分析
- 三次嘗試的共同假設是什麼？
- 這個共同假設本身是否可能是錯的？
- 前模型沒有考慮到的可能性是什麼？

### 4c. 程式碼邏輯追蹤
- 從錯誤發生點往上追蹤：資料從哪裡來？
- 在哪個確切步驟，預期行為和實際行為開始分歧？

### 4d. 環境與依賴確認
- 版本相容性是否有問題？
- 環境變數設定是否正確？
- 若有 Docker：服務依賴順序是否正確？

### 4e. SSOT 與介面一致性確認
- 相關模組之間的介面定義是否一致？
- 是否有 SSOT 違反（同一個定義出現在多個地方且不一致）？

### 4f. 根本原因結論

```
根本原因：[一句話明確描述]

詳細說明：[解釋為什麼前三次嘗試失敗，真正問題在哪裡]

前模型的盲點：[前模型一直假設問題在 X，但實際問題在 Y]

信心程度：[高/中/低] — [說明理由]
```

## ⏸ 審核點 DBG-A｜確認修復計畫

有效 `SUPERVISOR_DELEGATED` 委託內，主代理確認五維分析是否有原始證據、根因是否說明前三次
失敗、修復是否有新理由及 TDD 覆蓋。缺口交回分析角色補齊；通過後記錄 `SUPERVISOR_ACCEPTANCE`，
直接交實作角色進行步驟6。主代理可依證據處理範圍內技術分歧及非阻擋事項，不能放行必要證據
缺失或未解決的高嚴重度／阻擋問題。超出委託或達停止條件才返回人類。

其他模式維持人類審核：

```
暫停執行。
輸出：「根本原因分析與修復計畫已完成，請審核後確認可以開始執行修復。」
等待人類確認後才繼續步驟6。
若人類要求修改，回到步驟4重新分析。
```

## 步驟6｜執行修復（TDD）


可測行為先寫能重現 bug 的測試；依賴安裝失敗本身不算功能 RED。初始化早期環境故障
先保留可用的有效重現與必要檢查，依核准修復計畫處理，不為製造 RED 破壞正常骨架：
```bash
# Python
uv run pytest tests/ -v -k "test_[問題描述]"

# Jest
npx jest --verbose -t "[問題描述]"

# Vitest
npx vitest run -t "[問題描述]"

# 預期：FAILED（重現 bug）
```

執行修復後，重跑上方對應語言的同一條指令：
```bash
# 預期：PASSED
```

⚠️ 修復後測試仍失敗 → 禁止重複相同方向，必須回到步驟4重新分析。

**終止條件：** 同一未解問題回到步驟4的重新分析預設以 **2 輪為限**（含首次共 3 次分析機會）；
主代理模式的初始委託可明訂其他合理上限。這不是整份計畫的總修正次數，且更名問題或替換
執行者不會清零。無新證據，或達適用上限後仍無法收斂時，禁止再嘗試，改為執行：

1. 在除錯交班文件末尾追加「升級後仍未解決」段落，記錄每一輪的分析方向與失敗原因
2. 向人類報告：目前狀況、已排除的可能性、建議的下一步（例如：縮小問題範圍、拆成更小的任務、更換技術方案、或尋求人工協助）
3. 停止修復嘗試，等待人類決定

## 步驟7｜跑全部測試，確認通過


```bash
# Python
uv run pytest tests/ -v

# Jest
npx jest --verbose

# Vitest
npx vitest run
```

已適用且已建立的全部測試通過才繼續。有失敗 → 回步驟6並遵守同問題停止條件。
初始化依序尚待建立者依前述三態記錄補驗；零收集或空 fixtures 不宣稱功能已驗證。

## 步驟8｜靜態檢查


```bash
uv run ruff check .                   # Python
npx eslint .                          # JS/TS
uv run python scripts/guard_all.py          # SSOT
uv run python scripts/guard_security.py     # 安全性（S1–S9）
uv run python scripts/guard_dependencies.py  # Docker（若有）
```

已適用且已建立的必要檢查零錯誤才繼續；依序尚待建立與不適用依前述三態記錄，
不能把原已宣告必跑工具的失敗或缺失改稱不適用。

## 步驟9｜更新文件與交班記錄


### 9a. 在除錯交班文件末尾補充解決記錄


### 9b. 若根本原因涉及架構問題，新增 ADR

### 9c. 更新來源流程狀態

已有 HANDOVER.md 時更新狀態、精確中斷點、下一步與原事故連結；初始化早期尚無
HANDOVER 時只在已授權事故位置追加解決與補驗記錄，不提前建立後續骨架。
原 FAIL evidence 與先前結論保留，只追加本次結果；尚待補驗時不記初始化已完成。

```
✅ 除錯升級流程完成。

根本原因：[一句話]
修復方式：[一句話]
當前適用驗證：[實際命令與結果]
尚待建立／驗證：[項目、責任人與來源流程補驗步驟；無則明列無]
文件：[實際更新位置]

💡 提示：危機已解除，後續開發可切回原本使用的模型，不需要繼續用高階模型（節省成本）。

回到來源流程：[workflow]，從交班文件「精確中斷點」的步驟 [N／子步驟] 接續。
下一步：[接續中斷點的任務，或等待人類指示]
```

dev-workflow 事故：修復變更與原任務一併通過 DEV-B，依步驟13的實際授權交付。
project-init 事故：例如回 project-init 步驟 10-7，重新驗證該步驟並完成後續骨架驗收；
不得提前進 dev 或稱為 DEV-B。步驟13獨立核對 Git，步驟14才記初始化終態與後續範圍。
其他來源：回記錄的具體任務；來源不明先補足證據，不預設 dev。

主代理確認修復的原始結果、待驗安排與其餘工作，再派回原中斷點。Debug 不單獨 commit；
沒有相應 git init／stage／commit 授權時交付未提交候選，不因 Debug 結束而新增權限。
