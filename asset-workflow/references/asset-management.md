# 素材管理與交付

本檔是素材檔案放哪裡、怎麼命名與鎖定、怎麼交付與發佈的正本。基準的挑選與對照以同資料夾的
reference-review.md 為準。

## 五種狀態

| 狀態 | 判斷標準 | 存放位置 |
|---|---|---|
| 原始碼 | 人寫的、需要看差異 | git |
| 原始素材 | 無法重新產生（母帶、手繪原稿、QA 鎖定基準、核可的基準） | 自己做的：git，大型二進位檔用 LFS；外部取得的參考：repo 外的參考庫，git 只放清單 |
| 衍生檔 | 能從上面兩種重新產生 | 輸出資料夾（不進 git，刪掉後能整個重算） |
| 交付成品 | 某一版的正式結果 | repo 外的成品庫 |
| 發佈紀錄 | 成品發到了哪裡 | git（作品的成品紀錄檔） |

判斷口訣：

- 腳本會讀它，又無法重算 → 不能放輸出資料夾。
- 刪掉後能重算 → 一定放輸出資料夾。
- 能不能重算要實測，不要用猜的：重算一次，和原檔逐位元組比對。每次合成結果都不同的（例如帶隨機的音訊合成），
  核可的那一份就是無法重算的原始素材。

原始素材只有一份，衍生檔永遠由它產生，不手改衍生檔。

## 目錄骨架

專案可以有自己的最上層結構；每個作品至少分出下列位置，文件中的路徑一律寫成 `<作品>/…`。

```text
<作品>/
├─ README.md          目前版本 → 指令 → 檔案 → 作品內容
├─ 規格檔             規格與目前版本（版本號只寫在這裡）
├─ releases.json      每一版的狀態、tag、成品雜湊、核可與發佈紀錄
├─ 原始碼與腳本        固定的步驟名稱，不帶版本號
├─ art-bible.md       art bible（範圍是整個專案時放專案層）
├─ assets/            原始素材（LFS）
├─ reference-set.json ART-0 核可的基準清單（檔案在參考庫）
├─ masters/           核可且無法重算的母帶（LFS）
├─ baselines/         鎖定基準與雜湊清單
└─ reports/<版本>/    各版的迭代紀錄與審核報告
<輸出資料夾>/<作品>/   衍生檔：打包、中間檔、檢查圖
<參考庫>/<作品>/       基準與定錨圖（repo 外）
```

- 渲染等步驟用完中間檔就刪除，不讓輸出資料夾無限長大。
- 所有步驟都要能在 repo 裡直接執行；改完腳本後，從空的輸出資料夾把完整流程跑一遍才算數。
- 清空或刪除既有的輸出資料夾不在 AI 自動清理的項目內（見 dev-workflow 的 progress-record.md），先問人類，
  或改在新建的空資料夾跑；專案腳本刪掉自己剛產生的中間檔不在此限。

## 命名與版本

| 對象 | 規則 |
|---|---|
| 目前版本 | 只寫在作品的規格檔，腳本從那裡讀 |
| 正式版本 | `rNN`，兩位數 |
| 樣片 | `lookdev-sNN` |
| 原始碼 tag | `<作品>/rNN`；從舊壓縮檔還原的另用前綴（例如 `archive/<作品>/rNN`） |
| 成品檔名 | `<標題>_<長度>_<尺寸>_<版本>.<副檔名>`，語言版本放在標題後 |
| 程式檔名 | 不帶版本號；版本交給 git |

不用壓縮檔當版本控制；需要給別人一份原始碼時，從 tag 匯出。

## 成品庫

- 位置由專案宣告（寫在專案的 AGENTS.md 或作品 README），框架不規定磁碟或路徑。
- 結構：`<成品庫>/<作品>/<版本>/`，放成品、當時的審核圖與 `SHA256SUMS`。
- 成品一旦歸檔就不再修改；後續修正是新的版本。
- 成品庫不是暫存：任何清理（包括 dev-workflow 的暫存清理）都不碰成品庫。
- 成品庫和 repo 在同一顆硬碟時，提醒人類定期複製到別的硬碟。

## 參考庫

參考素材本身不進 repo（含 LFS）：放專案宣告的參考庫，repo 只存清單（來源、授權、SHA-256、大小）與量測設定。

- 位置由專案宣告（寫在專案的 AGENTS.md 或作品 README），框架不規定磁碟或路徑，但不能在 repo 裡面；
  腳本從宣告的位置讀。
- 結構：`<參考庫>/<作品>/<參考集>/`，放基準、定錨圖與 `SHA256SUMS`；核可後不再修改，換基準就是新的參考集。
- 參考庫不是暫存：任何清理都不碰它；也不推送、不上傳、不發佈（授權常不允許轉載原檔）。
- 參考庫通常只有一份：和 repo 在同一顆硬碟時，提醒人類定期複製到別的硬碟。檔案遺失時照清單的來源、
  依下載同意重新取得，核對 SHA-256，對不上就回 ART-0。
- 既有 repo 裡已經有的參考檔不再新增；搬出 repo 照該專案自己的計畫。

## 成品紀錄

每個作品一份 `releases.json`，每一版一筆，格式見 `assets/templates/releases.json`：

- 版本、狀態、日期；能重現這一版的 tag。
- 成品庫位置；每個檔案的名稱、用途、大小、SHA-256。
- ART-2 核可紀錄（日期、人類原話或來源、對應的候選 commit）。
- 發佈紀錄：平台、日期、網址、文案、上傳的檔案與雜湊。
- 重現限制等必要說明。

狀態：`wip` → `review` → `approved` → `published`；`retake` 退回重做；`superseded` 被後續版本取代。

## Git LFS

- 自己做的原始素材與母帶這類大型二進位檔用 LFS；LFS 的規則寫在 `.gitattributes`，和 commit 一起經 DEV-B。
  參考素材不進 repo，見「參考庫」。
- 推送 LFS 檔案前取得同意：遠端容量可能產生費用。推送屬於一頁計畫的 Git 範圍。
- 多人同時改同一個二進位檔時需要檔案鎖；LFS 的檔案鎖需要遠端支援，本流程還沒有驗證過。
- 要把既有的大檔搬進 LFS 而改寫歷史時，改寫與強制推送都要在 Git 範圍中單獨取得人類明確核准；改寫後確認工作目錄
  是實際檔案而不是指標檔，並用雜湊和備份比對。

## 鎖定與重新上鎖

- 已核可、不應再改的檔案記在鎖定清單（內容雜湊）；專案的 QA 檢查它沒有變。
- 檔案搬家或改路徑造成雜湊改變時，清單記下舊路徑、舊雜湊與原因，並用畫面比對證明外觀沒變。
- 本版刻意修改的檔案，先在計畫中列出並從鎖定清單移除；ART-2 核可後用新的雜湊加回去，
  這次重新上鎖放進 DEV-B 前的候選。下一版要改，得再刻意解鎖。

## 共用素材與範圍外的段落

改了共用的素材或程式，所有用到它的已核可作品與本次範圍外的段落，都要和已核可的版本逐段比對。

- 一頁計畫就列出用到的共用素材與程式，以及其他用到它們的已核可作品。
- 比對用畫面或聲音的逐段並排，容許範圍取自雜訊底線（選用外觀和原版共用同一支程式時，用一頁計畫核可的上限，
  見 reference-review.md）；只拿新舊兩張圖比，分不出是改壞了還是雜訊。
- 鎖定清單抓不到複製出去的程式：別處複製了同一段算法時，改原處就要一起改，並排比對才看得出接縫。
- 只想改一段卻會連帶改到範圍外時，用參數把範圍外的段落保持在上一版的設定，再用並排比對確認。
- 已核可的作品要有自己的鎖定基準，不能只靠主作品的 QA 涵蓋。

## 交付

ART-2 核可且 DEV-B 通過並合併後才算交付；commit、tag 與推送依授權的 Git 範圍，tag 只打在已合併且確認能重現的 commit，合併後改 repo 內的檔案要另過 DEV-B。

順序：

1. 候選放進成品紀錄（預定 tag 名、成品雜湊、成品庫位置、ART-2 核可紀錄）與重新上鎖。
2. DEV-B 審完整候選，通過後依授權合併。
3. 從合併後的 commit 重新產生成品，和 ART-2 核可的成品比對：能逐位元組重現的要求雜湊相同，不能的（例如 GPU 渲染）
   要在雜訊底線內；確認能重現。
4. 把成品複製到成品庫，核對 `SHA256SUMS`。
5. 3、4 都成功才在授權範圍內打 tag 並推送。任一失敗不打 tag，回報人類；修正成品紀錄等 repo 內容另過 DEV-B。

每一個交付的版本都要有 tag 再開始下一版；不要在同一個工作目錄連續做兩版而中間沒有快照。

## 發佈

- 發佈到外部平台由人類做，或逐次取得同意；發佈前跑專案宣告的平台限制檢查。
- 平台常會重新壓縮；成品庫永遠保存原始成品。
- 發佈後把發佈紀錄寫進成品紀錄、狀態改為 `published`；這是 repo 內的修改，另過 DEV-B。

## 第一次在專案使用

- 在一頁計畫中提出：作品的目錄骨架、輸出資料夾的 `.gitignore`、LFS 規則、成品庫與參考庫位置、art bible 的範圍、
  鎖定清單與成品紀錄的位置。
- 既有檔案先依五種狀態分類；能不能重算一律實測。搬家照上方「鎖定與重新上鎖」留紀錄。
- 這些都是 repo 內的修改，照常經過 DEV-B；專案還沒有量測或驗證工具時，先照 dev-workflow 做出來。
