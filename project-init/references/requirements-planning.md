# 需求與規格程序（步驟 0–5）

規劃新專案時讀取；已明確的當次需求與偏好直接沿用，不重複訪談。`references/` 與 `assets/` 以 Skill 根為基準。

## 步驟0｜需求引導對話（Brainstorming）


**啟動條件：** 使用者說出任何模糊的專案想法，例如「我想做一個…」「我需要一個可以…的東西」「幫我建一個…」

**目標：** 透過蘇格拉底式對話，把使用者模糊的想法引導成足夠清楚的方向，再進入步驟1的結構化訪談。

**原則：**
- 一次只問一個問題，等回答後再問下一個
- 根據回答決定下一個問題，沒有固定題數
- 問到能回答「這個專案要解決什麼問題、給誰用、核心功能是什麼」為止
- 語氣隨性，不要像在填表格
- 使用者說「差不多這樣」或「就這個意思」即可結束

---

> 📋 **引導問題庫**（依情況選用，不必全問）見 `references/interview-guide.md`。
---

### 引導結束的判斷標準

當 AI 能回答以下三個問題，即可結束步驟0，進入步驟1：

```
1. 這個專案要解決什麼具體問題？
2. 主要使用者是誰？
3. 最核心的功能是什麼（1-3個）？
```

結束時向使用者確認：
> 「好，讓我確認一下我理解的方向：[一段話摘要]。大致上是這樣嗎？」

使用者確認後，宣告：
> 「清楚了，我們來把這個想法具體化。」

---

### 規模判斷與流程調整

確認方向後，AI 依下列標準評估專案規模：

**小型專案**（符合以下多數條件）：
- 個人使用或最多 2 人
- 預估代碼量 < 500 行
- 無外部服務整合
- 無需部署到生產環境

→ AI 詢問：「這看起來是個小型工具，可以用小型專案初始化（跳過 CI/CD 設定和 MkDocs，文件從簡）。你偏好完整專案初始化還是小型專案初始化？」

- **選擇小型專案初始化**：步驟4（CI/CD）直接跳過；步驟7g（mkdocs.yml）跳過；步驟8跳過 MkDocs 依賴；步驟11跳過；文件骨架只建立最必要的部分（spec.md、SSOT README、交班文件）。
- **選擇完整專案初始化**：執行原始14步驟流程。

**中型以上**（有外部整合、多人協作、或需要部署）：直接執行完整14步驟流程，不詢問。

---

然後進入步驟1（結構化需求訪談）。

---

### AI 禁止行為

- ❌ 一次拋出多個問題
- ❌ 使用者還沒說清楚就跳到技術討論
- ❌ 自己假設使用者的需求然後繼續
- ❌ 問題問得像在填表格（「請問您的目標使用者是？」）
- ❌ 使用者說「差不多」就立刻跳到下一步，應先摘要確認

---

## 步驟1｜需求訪談


先核對當次已知需求；只詢問下列尚未清楚的事項（一次問一個），不把清單當作必問問卷：

1. 這個專案要解決什麼問題？目標使用者是誰？
2. 最核心的功能是什麼？（列出3-5個）
3. 有沒有外部系統需要整合？（資料庫、API、第三方服務）
4. 預期的使用規模？（個人用、小團隊、公開服務）
5. 有沒有特定的限制？（平台、語言偏好、預算、時程）
6. 是否需要使用者介面？（純後端、Web、CLI、行動裝置）

將需求整理進規格；仍有歧義時才釐清。INIT-A／INIT-B 的必要審核保持，已知需求不逐項重問。

---

## 步驟2｜AI 提議技術棧


### 步驟2-0｜專案類型確認（新手引導）

專案類型仍不清楚時才詢問；能從當次需求判斷則直接使用下方路徑表：

> 「你大概想做什麼類型的東西？（選最接近的就好，不需要完全準確）
>
> 1. **Web API / 後端服務** — 提供資料或功能給其他程式或前端呼叫（例如：RESTful API、資料查詢服務）
> 2. **有介面的網站 / Web App** — 使用者可以在瀏覽器操作的應用（例如：管理後台、訂單系統）
> 3. **聊天機器人 / Bot** — 接在 LINE、Discord、Telegram、Slack 上的自動回覆機器人
> 4. **資料分析 / 爬蟲 / 自動化腳本** — 定期執行、處理資料、從網站抓資料（例如：報表自動化、資料清洗）
> 5. **命令列工具** — 在終端機執行的程式（例如：一鍵備份工具、批次處理腳本）
> 6. **全端應用（前端 + 後端）** — 同時包含網站介面和後端 API
> 7. **我不確定 / 幫我判斷** — AI 根據需求訪談結果推薦」

根據選擇，執行對應路徑：

| 選擇 | 路徑 |
|------|------|
| 7（不確定）或訪談結果已足夠清楚 | 直接推薦一套，不呈現比較表（見下方「各類型預設推薦棧」） |
| 1、4、5 | 以 Python 後端棧為主，呈現 1-2 個選項並說明差異（不是 3 個） |
| 2、3、6 | 詢問前端 / Bot 平台偏好，再呈現對應棧選項 |
| 使用者能描述技術偏好 | 正常呈現 2-3 套比較表 |

> 📋 **各類型預設推薦棧（AI 參考用）** 見 `references/tech-stack-recommendations.md`。
---

根據需求訪談結果提議技術棧方案。**預設提議 2-3 套**；若命中步驟2-0 路徑表的直推情境（使用者不確定、或訪談結果已足夠明確），**直接推薦 1 套即可，不算違規**。每套方案必須包含：

**方案格式：**
```
### 方案 [X]：[方案名稱]

| 層次 | 技術選擇 | 選擇理由 |
|------|---------|---------|
| 語言 | | |
| 框架 | | |
| 資料庫 | | |
| 測試 | | |
| 文件 | MkDocs | 配合現有流程 |
| 靜態檢查 | ruff（Python）或 ESLint（JS/TS）| 配合現有流程 |
| 套件管理 | | |

**優點：** [列出]
**缺點：** [列出]
**適合情境：** [說明]
```

固定採用的項目（不需列入選擇）：
- 文件系統：MkDocs
- Python 靜態檢查：ruff
- JS/TS 靜態檢查：ESLint
- 版本控制：git

固定使用版本控制工具不授權 git init、stage 或 commit。現有 Python／JS／TS 是第一版
具體工具流程；其他語言可採共通原則，但 INIT-A／INIT-B 必須揭露模板、測試、lint、型別
及安全掃描缺口，補齊本專案必要驗證方式前不承諾自主完成或全面支援。

---

### 新手使用者的技術棧引導

若使用者在訪談中表示不了解技術選項（說「我不懂」「你幫我選」「隨便你」等），AI **不呈現比較表**，改為直接推薦：

> 「根據你描述的需求，我推薦方案 [X]：[方案名稱]。
> 選它的原因是：[一句白話說明，例如「這是目前最多人用、出問題最容易找到解法的組合，適合你這個規模的專案」]。
> 你不需要了解技術細節——確認這樣可以嗎？」

使用者說「可以」或「好」即繼續，不需要使用者理解技術選擇的含義。

## ⏸ 人類審核點 INIT-A｜技術棧確認

```
暫停執行。
多方案時輸出：「以上為 [X] 套技術棧方案，請選擇方案編號或告知調整方向。」
單一推薦時輸出：「以上為推薦方案，回覆『可以』即採用，或告知想調整的方向。」
等待人類明確選定或同意後才繼續步驟3。
```

## 步驟3｜Docker 需求確認


當次對話尚未確定 Docker 需求時才詢問：
> 「這個專案需要 Docker 嗎？（例如：需要隔離環境、多個服務、或部署到容器平台）」

- **需要** → 記錄，步驟6建立 Docker 骨架檔案（`docker/Dockerfile`、專案根 `docker-compose.yml`），步驟8加入 pyyaml 依賴，步驟10生成 Docker 依賴性檢查腳本
- **不需要** → 記錄，跳過 Docker 相關設定

---

## 步驟4｜CI/CD 需求確認


當次對話尚未確定 CI/CD 需求時才詢問：
> 「這個專案需要 CI/CD 嗎？如果需要，請告知使用的平台（例如：GitHub Actions、GitLab CI、Bitbucket Pipelines、CircleCI、Jenkins、自建等）。」

- **需要** → 記錄平台，步驟11建立對應設定檔
- **不需要** → 跳過步驟11

---

## 步驟5｜撰寫完整專案規格文件


建立 `docs/spec.md`：

> 📄 **範本**：`assets/templates/spec.md` —— 依範本結構（專案概述／功能需求／技術規格／環境規劃／資料庫變更管理／介面規格／資料模型／非功能需求／限制與假設／驗收標準）填入訪談與審核結果後建立 `docs/spec.md`。

填寫範本的「品質與初始化驗收」表：品質／成果項目、語言或框架適用條件、驗收方式／命令
正本位置、初始化完成前必驗與未覆蓋限制。共通工程原則和技術棧規則以共同 AGENTS 為正本；
spec 記核准需求與適用理由，實際驗證命令由專案 AGENTS 的「技術棧與執行命令」引用既有
package／工具配置，spec 只引用項目，不建立衝突命令副本或另一份 quick 宣告。

至少涵蓋模組責任與依賴方向、測試可執行與最小骨架能力、適用靜態檢查、必要守衛與文件
建置、CI/CD。可執行骨架須有對應成功與失敗的最小行為測試；空 fixtures 或零測試收集
不算功能驗證。不適用須附理由，不能省略已宣告 ssot／security 或條件式 docs validators。
CI/CD 骨架生成與遠端實跑分列；後續功能、部署或尚無工具覆蓋的部分據實記錄。

---

## ⏸ 人類審核點 INIT-B｜規格確認

```
暫停執行。
輸出：「spec.md 已完成，請審核專案規格，確認無誤後告知可以開始建立專案結構。」
等待人類確認後才繼續步驟6。
若需修改，更新 spec.md 後再次等待確認。
```

INIT-B 由人類確認完整規格及上述品質／初始化完成條件；主代理不能代審 INIT-A 或 INIT-B。
可在同一份摘要另列：「規格通過後，是否委託主代理安排執行者完成步驟 6–12、範圍內執行
計畫與 DBG-A、修正及骨架最終驗收；交付是否包括 Git 或後續功能。」已有明確決定直接沿用，
不重問；只確認規格不等於主代理委託。明確選用時才讀 `references/supervised-initialization.md`，
未選用則維持原路線；兩個人類 gate 完成前均不得啟用骨架迴圈。
