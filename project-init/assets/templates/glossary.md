# 術語表（白話版）

> 這裡解釋 ToukaDev 流程中會出現的技術詞彙。
> 看到看不懂的詞，在這裡找白話說明。不需要完全理解這些概念——AI 會幫你做，你只需要知道「它在幹嘛」。

---

## 開發方法論

**TDD（Test-Driven Development，測試驅動開發）**
先寫「驗收條件」再寫程式碼。就像先定義「蛋糕做好的標準是什麼」，再開始烤，確保最後做出來的就是你想要的。dev-workflow 的步驟5-8 就是在做這件事。

**SDD（Specification-Driven Development，規格驅動開發）**
在寫任何程式碼之前，先把需求寫成正式文件。這個框架使用的核心原則，project-init 的前半段都在做這件事。

**SSOT（Single Source of Truth，單一事實來源）**
每個數值、設定、常數只在一個地方定義，其他地方都去引用那一個。防止「A 說路徑是 /app/data，B 說是 /data」這種不一致導致出錯。guard_all.py 會自動檢查違規。

**ADR（Architecture Decision Record，架構決策記錄）**
記錄「為什麼當時這樣決定」的文件。例如「為什麼選 PostgreSQL 不選 MySQL」，讓未來的 AI 和你自己不需要重新想一遍、不會重複踩同樣的坑。

**SOLID**
五個程式碼設計原則的縮寫（單一職責、開放封閉、里氏替換、介面隔離、依賴反轉），讓程式碼容易維護和擴充。AI 在設計程式時會自動遵守，你不需要理解細節。

**Gherkin**
一種用來描述功能需求的格式，用「Given（假設情境）/ When（當這件事發生）/ Then（應該得到這個結果）」三段式寫清楚期望行為。dev-workflow 用這個格式讓 AI 確認它理解你的需求。

**DRY（Don't Repeat Yourself）**
不重複自己。同一段邏輯只寫一次，避免「複製貼上」導致改了一個地方忘記改另一個。

**重構（Refactor）**
在功能不變的前提下，整理程式碼讓它更清楚、更好維護。像是整理房間但不改變家具功能。dev-workflow 步驟8 就是在做這件事。

## 美術素材流程

**先定基準（參考基準）**
美術沒辦法先寫「好不好看」的測試，所以 asset-workflow 把「先寫測試」換成「先定基準」：開工前你和 AI
來回確認一組參考（例如十張概念圖、一段實拍影片）和衡量「接近」的方式，之後 AI 自己對照基準逼近。

**ART-0／ART-1／ART-2**
asset-workflow 的三個人類審核點：ART-0 核可基準與這次的計畫，ART-1 看試作品，ART-2 核可成品。
中間版本 AI 不會請你看圖；量化指標全部通過也不等於核可，量不到的差異會寫進報告由你決定。

**成品庫**
放每一版正式成品的資料夾，在 repo 外，位置由專案自己宣告。成品歸檔後不再修改，任何清理都不會碰它。

**Git LFS（大型檔案儲存）**
讓 git 管理影片、圖片、音檔這類大型檔案的擴充：repo 裡只放指標，實際檔案另外存放。
推送到遠端可能產生容量費用，所以推送前會先問你。

**tag（版本標籤）**
貼在某個 commit 上的名字（例如 `作品/r03`），之後隨時能回到那一版的原始碼。
asset-workflow 只在合併後、確認能重現那一版的 commit 上打 tag。

## 使用者可見流程名稱

**精簡輸出模式**
只縮短 AI 的說明文字，不會跳過 TDD、guard、DEV-A、DEV-B 或任何授權點。
`模式：精簡` 是保留的 machine token；舊稱「精簡模式」仍可辨識。

**文件快速路徑**
只適用純文件或 typo 級修正；碰到程式行為、SSOT 或測試就必須回完整 DEV-A。
舊稱「`/quick`」「輕量變更路徑」或「輕量路徑」仍可辨識。

**小型專案初始化**
project-init 的小型設定，可省略 CI/CD 與 MkDocs；它不會改變後續開發的審核或授權要求。
舊稱「輕量流程」仍可辨識。

## AI 協作

**高階模型（High-tier Model）**
同一家 AI 服務通常提供多個等級的模型：回應快、成本低的日常款，和速度慢、成本高但推理更深的旗艦款。
debug-escalation 說的「換高階模型」，就是切換到你的工具**當下提供的最高階選項**（模型選單通常會標示等級或價格）。
具體型號更新很快，框架刻意不寫死名稱；不確定哪個最高階，直接問你的 AI 工具即可。
主代理代審的 Debug 可以改派適合問題的新分析上下文，同模型也可用；不以取得更高價模型為前提。

**主代理代審**
使用 SUPERVISOR_DELEGATED；結論為 SUPERVISOR_ACCEPTANCE，不是嚴格獨立 reviewer。
DEV-A／DEV-B 的預設模式。主代理把計畫整理成一頁白話版，先交非作者的 reviewer 審，再請人類核准；
核准即委託主代理在範圍內派工、審核、退回修正並整體驗收，DBG-A 隨所屬任務的委託。
寫的人和審的人不能是同一個：執行者的成果由主代理審，主代理自己寫的內容交給新上下文的 reviewer。
會寫檔的平行工作各用隔離工作區；主代理維持本機進度紀錄，讓人類不用開口問就看得到進度。
有效範圍內連續推進，超出委託或無法收斂才返回人類，最後統一回報。可使用子代理、其他對話、
CLI 實例或等效方式，不要求新的工作流框架。人類可隨時改選其他模式；平台沒有可用的派工方式時，
改列出五種模式並建議 HUMAN_AI。其他模式的 reviewer 資格保持原義。

**進度紀錄與進度網頁**
主代理代審時，主代理在本機 `.toukadev/progress/` 維持一份文字進度紀錄，每次更新後用 dev-workflow 附的
小程式轉成網頁。雙擊同一資料夾的 `index.html`，就能看誰在做、誰在審、哪些已驗收、要你決定什麼，
以及還沒清的暫存；用一般瀏覽器開啟時網頁每 5 秒更新，並顯示紀錄最後更新是幾分鐘前（只顯示快照的工具
會在網頁上提醒）。它只是工作檢視，不是目前交班，也不是授權。

**暫存項目**
任務中 AI 建立的工作資料夾、分支與暫存檔，一建立就登記，結束時清掉或寫明保留理由，清完才算完成。
AI 只用安全的刪法清理四種本任務自己的項目；dev、main 這類共用分支永遠不刪，其他一律先問你；
工具自己的快取（例如 Codex 的對話紀錄、套件快取）由你決定。

**改進紀錄**
流程或規則出問題時（照做或沒照做而出大錯、問題到合併後或由你才發現、你對同一件事第二次糾正、
某個步驟白做工），AI 在專案資料夾的本機 `.toukadev/lessons/` 記一筆，不進版控。紀錄只是證據，
AI 不會因此自己改規則；記完繼續原本的工作。

**改進任務**
由你啟動（例如說「開始改進 ToukaDev」，或在大任務的一頁計畫核准做完後跑改進）：AI 讀累積的改進紀錄，
整理成一頁白話計畫，寫出每組問題要怎麼改或為什麼不改；你逐條核准後，才照一般 dev-workflow 修改 ToukaDev。
其他時候，紀錄值得處理時 AI 只提醒一句，不會自己開始。

**白做工**
某個步驟或規則花了時間、費用或你的注意力，卻沒有作用，例如問了不必問的事、重複確認、檢查程式誤判擋下
正常工作；規則缺漏或誤判，雖然沒出大事卻迫使你介入或停下工作，也算。白做工也會記成改進紀錄；
但審核點這類受保護的規則不會只因白做工就被拿掉，會先想辦法降低成本。

**獨立 reviewer（獨立審核者）**
不是讓原本寫計畫或程式的 AI 再看自己一次，而是交給另一個全新、唯讀的 AI 工作階段，
直接檢查需求、計畫、修改內容與測試證據。工具還必須能禁止它修改檔案或再叫其他 agent；
無法證明時不能稱為獨立 reviewer。它負責技術判斷，人類仍決定需求、成本與不可逆行動。

**模型證據（Model Evidence）**
原四模式的 AI reviewer 無法確認實際使用的模型時，AI 必須說明；這時結論最高 `PASS_WITH_NOTES`，
不能滿足 `AI_DELEGATED` 的自動繼續或 commit，避免把「指定了模型」誤寫成「模型一定沒變」。
主代理代審不把 actual model／effective sandbox 的 runtime attestation 當入口門檻，也不宣稱
取得未知證明；任務完成條件所需的技術證據仍須補齊。

**跨服務資料傳輸同意**
把審核內容送到其他 AI 服務或 premium reviewer 前，AI 必須說明送什麼、送去哪、對方有無資料保證，
並取得你明確同意；無法說明對方條件時不得傳送。

**對抗式多代理複審（Adversarial Review）**
同時請多個 AI 從不同角度找問題，例如一個看需求、一個看測試、一個看安全性。
這比單一審核花費更多額度，所以每次都必須先取得人類明確同意。`HIGH` 只有命中具體風險
條件才會建議，`CRITICAL` 也只強烈建議一次，拒絕後不會無理由重複詢問。
只有命中觸發清單時，主代理才會在一頁計畫中把它單獨列成選項；你單獨選它才算同意。

**跨 session 背景與當次授權**
`AGENTS.md`、交班文件與平台 Memory 可以保存長期規則、偏好與歷史，讓新的 AI 對話快速接手；
但它們不能代表你這次同意了審核模式、資料傳輸、多代理、開始實作或 commit。這些高影響決定
在舊模式依逐次規則確認；主代理模式有可核對的原始委託及派工來源時，可續接同一任務，
不因換對話、執行者或等效工具重問。另一份計畫、取消或超出範圍不能沿用；背景紀錄不產生新權限。

**變更風險（Change Risk）**
這次工作本身可能造成多大影響，分為一般、高風險、關鍵風險。
它用來決定要多強的 reviewer、是否建議多代理，不代表工作已經通過或失敗。

**問題嚴重度（Finding Severity）**
reviewer 找到的某一個問題有多嚴重。低或中等問題可能只是注意事項；
高或阻擋問題必須修正，不能靠投票或一句「接受風險」跳過。

**審核結果（Review Verdict）**
這一輪審核的總結，例如 `PASS`（通過）、`PASS_WITH_NOTES`（通過但有注意事項）、
`CHANGES_REQUIRED`（需要修改）或 `BLOCKED_OR_UNKNOWN`（目前無法可靠判斷）。

## 工具與環境

**git**
版本控制工具。記錄每次程式碼的修改，可以隨時回到過去某個時間點。像是 Word 的「版本歷史」但更強大。

**commit**
把這次的修改存進 git 紀錄的動作。像是儲存遊戲進度。每次 dev-workflow 完成都會做一次。

**branch（分支）**
git 的「平行時間線」。在分支上修改不影響主線，確認沒問題再合併進去。
多個 AI 同時改檔案時，每個 AI 各用自己的分支和工作資料夾（git worktree），不會改到彼此的檔案。
其他任務或其他人會使用或接手的分支（例如 dev、main）叫共用分支；任何成果合併進共用分支前都要通過 DEV-B。
這些由 AI 處理，你了解概念即可。

**CI/CD（持續整合/持續部署）**
每次上傳程式碼時自動跑測試、自動部署的機制。確保沒有人「不小心傳了壞掉的程式碼上去」。project-init 步驟11 會幫你建骨架。

**Docker**
把你的程式和它需要的所有環境打包在一起的工具。確保在你電腦能跑、在伺服器也能跑，不會出現「我的電腦沒問題但伺服器掛了」的狀況。

**Docker Compose**
管理多個 Docker 容器（例如同時跑「後端 API + 資料庫」）的工具，用一個設定檔描述它們的關係。

**虛擬環境（Virtual Environment）**
把這個專案的工具和套件，和你電腦其他東西隔離開來的機制。避免「專案 A 需要套件版本 1.0，專案 B 需要 2.0」互相衝突。

**環境變數（Environment Variable）**
不寫死在程式碼裡的設定值，例如 API 金鑰、資料庫密碼。放在 `.env` 檔案裡，不上傳到 git。

**.env 檔案**
存放秘密設定值（API 金鑰、密碼）的檔案。絕對不能上傳到 git，否則會洩漏。專案會有 `.env.example` 作為範本。

**uv**
Python 的套件管理工具，比傳統的 pip 更快。用來安裝和管理 Python 相關工具。AI 會用 `uv run` 執行指令。

## 測試相關

**單元測試（Unit Test）**
測試一個很小的功能單元（例如「這個計算函式算出來對嗎」），不依賴外部服務。速度快，最多的測試類型。

**整合測試（Integration Test）**
測試多個功能組合在一起的行為（例如「使用者登入後能不能看到訂單」）。速度較慢，測試更真實的場景。

**冒煙測試（Smoke Test）**
快速確認整個系統基本功能還活著的測試。就像電器插上電後先看有沒有冒煙，再做細部測試。dev-workflow 步驟11 會跑這個。

**mock（測試替身）**
測試時用假的元件替換真實的外部服務（例如用假的資料庫代替真實資料庫），讓測試快速且可重複執行。

**pytest / Jest / Vitest**
測試框架。pytest 給 Python 用，Jest/Vitest 給 JavaScript/TypeScript 用。執行測試、顯示哪些通過哪些失敗。

## 靜態檢查工具

**靜態檢查（Static Analysis）**
不執行程式碼就能找出問題的工具，像是文法檢查器。dev-workflow 步驟9 會執行這些工具。

**ruff**
Python 程式碼的自動檢查工具，找出格式問題、未使用的變數、潛在錯誤等。

**ESLint**
JavaScript/TypeScript 的自動檢查工具，功能和 ruff 類似。

## 框架與平台

**FastAPI**
Python 的 Web API 框架。寫後端 API 用的，優點是會自動產生 API 文件（OpenAPI 格式）。

**React**
JavaScript 的前端框架。做有介面的網站（使用者可以在瀏覽器操作的那種）用的。

**Click**
Python 的命令列工具框架。讓你的程式可以在終端機用 `python myapp.py --help` 這樣的方式執行。

**MkDocs**
把 Markdown 文件自動轉成好看網站的工具。用來建立專案的文件網站。

## 部署與環境

**Staging（暫存環境）**
介於「你的電腦（開發環境）」和「正式上線（production）」之間的測試環境。
讓你在真正開放給用戶之前，先在接近正式的環境裡確認一切正常。小型專案可以省略，直接從開發跳到正式。

**Migration（資料庫遷移）**
當你需要修改資料庫結構（例如新增一個欄位、改變一個欄位的型別），用來記錄這個「改動步驟」的腳本。
就像 git commit 記錄程式碼的版本，migration 記錄資料庫結構的版本。沒有它直接改資料庫，正式環境就會和開發環境不一致。

**Alembic**
Python 專案最常用的 migration 工具，和 SQLAlchemy ORM 搭配使用。
它能自動偵測你的資料庫模型有什麼改動，並生成對應的 migration 腳本。

## 架構概念

**API（Application Programming Interface，應用程式介面）**
不同程式之間溝通的方式。例如前端呼叫後端拿資料，就是透過 API。你可以把它想成「服務員」，你告訴它你要什麼，它幫你去拿。

**RESTful API**
目前最通用的 API 設計風格，用 GET（拿）/ POST（新增）/ PUT（修改）/ DELETE（刪除）等動作操作資源。

**OpenAPI / Swagger**
描述 API 規格的標準格式。FastAPI 會自動產生，讓前端知道後端有哪些 API 可以呼叫、要傳什麼參數。

**webhook**
當某件事發生時，自動通知你的程式的機制。例如「有人在 LINE 傳訊息時，LINE 伺服器自動通知你的 Bot」。

**JWT / Token**
一種驗證使用者身份的方式，像是數位版的「入場券」。使用者登入後拿到票，之後每次請求都帶著票，伺服器驗票確認身份。

**CORS（跨來源資源共享）**
瀏覽器的安全機制，防止 A 網站偷偷呼叫 B 網站的 API。後端需要設定允許哪些來源的請求。

**型別提示（Type Hint）**
在程式碼裡標記「這個變數應該是數字/字串/物件」的語法。幫助 AI 和靜態檢查工具發現型別錯誤。

**依賴注入（Dependency Injection）**
一種讓程式碼不依賴具體實作、便於測試的設計方式。AI 在設計程式時會自動使用，你不需要理解細節。

**ORM（Object-Relational Mapping）**
讓你用 Python 物件操作資料庫，不需要直接寫 SQL 語法的工具。SQLAlchemy 是 Python 最常用的 ORM。

**middleware（中介軟體）**
在請求到達主程式之前，先做某些處理的程式碼。例如「每個請求都先驗證 Token 是否有效」。

## 文件與交班

**Current handover（目前交班）**
根 HANDOVER.md 只保存目前狀態、阻礙、下一步與精確連結；狀態改變才更新。
