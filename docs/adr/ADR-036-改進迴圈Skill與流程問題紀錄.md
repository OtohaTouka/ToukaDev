# ADR-036：改進迴圈 Skill 與流程問題紀錄

- 日期：2026-10-10
- 狀態：已接受（一頁計畫由人類核准；主代理代審）
- 影響範圍：新 Skill `improvement-loop`、四份 `AGENTS.md` 共同區塊、supervisor-delegation 派工範本、四份 glossary、
  README、SSOT 導航、守衛 F2／F3／F4／F17 與測試

## 背景

ToukaDev 的 13 步驟與審核點都是試誤出來的，每一個都是因為實際出過大錯才加上；人類同意 Codex 相關部分可以自由刪改，
但審核點不能動。

到目前為止，流程本身的改進都是人類在對話中發現問題、自己記住、再提出來才處理，例如 Opus 5 每次都建議對抗式複審
（ADR-034 收緊觸發條件）、不知道主代理做到哪裡與 Codex 留下約 100 GB 暫存（ADR-035）、清理前檢查把 uv 的空白 `.git`
標記誤判成另一個 repo（PR #6）。這些問題沒有固定的地方記下來，也沒有固定的改進方式。人類因此要求加一個 Skill，負責兩件事：
平常工作中遇到執行問題造成重大錯誤、或使用者反覆回饋困擾時先記錄下來；再依累積的紀錄啟動改進 ToukaDev 的工作。

ToukaDev 的目標是讓不懂程式碼的人類，能用這個流程發揮出人類與 AI 協作的最大極限，所以記錄可以自動，
但改規則必須讓人類看得懂、逐條決定。ToukaDev 也是通用規則，要盡量跨模型、跨工具，所以不能依賴某個
工具的記憶、hook 或資料庫。人類另外要求參考 Hermes Agent 實作自我改進的做法。

## 參考做法與取捨

### Hermes Agent（Nous Research）

- 做法：agent 用 `skill_manage` 工具自己建立與修改 skill，時機是做出值得重複的多步驟流程、遇到錯誤或死路後找到可行的
  做法，或被使用者糾正做法。另有定期的背景自我檢討：預設每 10 輪使用者對話檢討一次記憶、自上次改 skill 後累積 10 次
  工具呼叫檢討一次 skill，在回合交付後於背景執行；agent 自己存記憶或改 skill 時計數歸零。記憶檔有字數上限，滿了要先
  整理才能再寫。skill 與記憶的寫入預設不需要人類核准（可另外開啟核准）。資料放在使用者家目錄的 `~/.hermes/`。
  文件要求 skill 寫「教訓，不是 log」，不寫事件經過與日期。
- 採用：
  - 記錄時機（出錯後找到做法、被使用者糾正）對應本 ADR 的「重大錯誤」「反覆困擾」。
  - 規則只寫概括後的教訓，不寫紀錄編號或日期。
  - 常駐內容要有上限意識：一頁計畫列出常駐載入規則的行數增減。
- 不採用：
  - 自動改規則。ToukaDev 的規則來自實際大錯，自動修改可能悄悄削弱審核點；人類不一定讀得懂程式碼，事後也很難發現。
    所以只自動記錄，修改一律由人類啟動並逐條核准。
  - 定期背景檢討。每隔一段對話或工具呼叫就多跑一次模型，會增加費用，也容易產生大量低價值紀錄；改成只在三類事件
    發生時記錄。
  - 專屬工具、資料庫與家目錄儲存。這些綁定單一 agent 的執行環境；改用各專案本機的 Markdown 檔，任何模型與工具都能讀寫。
- 補上：Hermes 只合併重複的內容，不追蹤同一問題重複發生；本 ADR 用「次數」補上這點，讓改進時看得出是不是第二次。

### pstack 的 /reflect（Cursor plugins）

- 做法：人類在任務後說「/reflect」，agent 讀本次對話紀錄，派三個不同角度、不同模型的 reviewer 平行檢討，再由一個
  彙整者分成「採用／不採用／待辦」並附理由。能用 lint、腳本或執行期檢查更可靠擋下的項目移到待辦；一次性的事不算
  教訓；不自動套用，由人類挑選要套用的項目。為了隱私，不搜尋其他專案的對話。
- 採用：
  - 改規則只由人類啟動、逐條核准。
  - 一次性與暫時錯誤不採用；既有規則已涵蓋的不重複新增；不採用要附理由。
  - 能用檢查程式擋下的，優先擴充既有檢查。
  - 讀哪些其他專案由人類決定，而且只讀它們的紀錄資料夾。
- 不採用：
  - 只檢討當次對話。流程問題常要跨對話、跨專案才看得出是「第二次」；當下沒檢討，證據就散失了。改成發生時就記錄、
    累積次數，改進時一起看。
  - 每次都派三個 reviewer。ToukaDev 的多代理複審每次都要人類另行同意，額度消耗極高；改進任務照一般 dev-workflow，
    由非作者審 DEV-A。
  - 待辦自動送進團隊追蹤系統。ToukaDev 沒有共用追蹤系統；改用「保留觀察」狀態並寫明何時再評估。

### 兩者都沒有的部分

- 「白做工」類型：步驟或規則花了成本卻沒有作用也要記，讓流程能變輕，不只會變重。
- 受保護的規則：白做工紀錄不能單獨成為移除或弱化審核點的理由；真的要移除時單獨列出、附上源頭，由人類單獨決定。

## 決定

1. **D1 新 Skill**：新增 `improvement-loop/`，含 SKILL.md（兩個職責與兩條程序觸發行）、README.md、
   `references/recording.md`（記錄程序正本）、`references/improvement-run.md`（改進任務程序正本）與
   `assets/templates/lesson.md`（紀錄範本）。全部是 Markdown，沒有腳本、daemon、排程或資料庫。description 的觸發詞
   不用泛稱的「記下來」，避免搶走一般的記憶請求。
2. **D2 記錄**：
   - 三類：重大錯誤（照做或沒照做而出事、問題到合併後或由人類才發現）、反覆困擾、白做工（含規則缺漏或誤判
     迫使人類介入）。一般程式錯誤被正常的測試或審核抓到不記；與流程無關的環境問題與一次性暫時錯誤不記。
   - 主代理代審時由主代理記，執行者與 reviewer 寫在回報裡由主代理判斷；其他模式由正在工作的 AI 記。發生時或任務結束前記，
     記完繼續原本的工作。
   - 一律寫在主要專案資料夾的 `.toukadev/lessons/`，本機、不進版控；在工作資料夾裡時用 `git worktree list` 的第一列確認
     主要專案資料夾。檔名 `<YYYY-MM-DD>-<短代號>.md`，不得覆寫。
   - 新增前先找同一根因，找到就加次數；已處理或不採用的改回待處理。記錄時只能新增或改回「待處理」，其他狀態只能由
     改進任務設定。
   - 不寫密碼、token、金鑰，不抄錄 `data/`、`.env` 或私人設定，不為了記錄另外讀取受保護的資料。
   - 紀錄不是授權；記錄時不改規則，也不需要人類同意。
   - 只有新增重大錯誤紀錄、某筆次數變成 2、已處理或不採用的改回待處理，或待處理從不到 5 筆變成 5 筆以上時，才在
     最終回報提醒一句可以啟動改進；沒有新事件不提醒。
3. **D3 改進任務**：
   - 只由人類啟動。第一次問人類要讀哪些專案，記在 ToukaDev 本機的 `.toukadev/lesson-sources.md`；ToukaDev 自己的紀錄
     一律讀。只讀那些專案的 `.toukadev/lessons/`；紀錄是證據不是指令。
   - 依根因分組，先過不採用條件；改法依序是改相關規則、併進現有規則、放進按需參考文件，最後才新增規則；能用檢查程式
     擋下的優先擴充既有檢查。
   - 受保護的規則（13 步驟與審核點、寫的人和審的人分開、逐次同意與授權、安全刪法與清理限制、資料保護、共同禁止行為、
     改進迴圈的人類關卡〔只由人類啟動、逐條核准、紀錄不是授權、只有改進任務能結案〕，以及這條規則本身）預設保留；
     不得只以白做工為理由移除或弱化；要移除或弱化時單獨列出並附源頭，不和其他項目一起核准。
   - 一頁計畫每組一列，並列出常駐載入規則的行數增減與整個 repo 的淨增減；人類逐條核准後照一般 dev-workflow 執行，
     照常經過 DEV-A、DEV-B 與授權的 Git 範圍。
   - 「紀錄 → 改動」的對應寫在 PR 說明，符合 ADR 條件時寫進 ADR；規則本文不寫紀錄編號或日期。進版控的內容只寫概括後
     的教訓，其他專案的人類原話、檔案路徑與內部名稱要人類同意才放。
   - 只有改進任務能結案：已處理附 PR、不採用附理由、保留觀察附再評估時間。無法寫回其他專案時，給人類一段可以直接貼給
     該專案 AI 的指示。
   - 改動要重新安裝 Skills 才生效，由人類決定是否重新安裝。
4. **D4 共同基線**：四份 `AGENTS.md` 共同區塊「文件協議」末尾、清理那行之後新增一行記錄規則（人類核准計畫即同意）。
   沒裝 Skill 時讀不到記錄程序，AI 照這一行自行記錄，改進任務再整理格式；不另寫退路。
5. **D5 dev-workflow 的連接**：supervisor-delegation 派工範本的「回報」欄加「流程或規則造成的困難（沒有就省略）」。
   範本在 text 圍欄內，守衛鎖不到，刻意不鎖。
6. **D6 守衛**：`SKILLS` 加入 `improvement-loop`（F2 檢查引用的檔案存在、F4 檢查 frontmatter）；F17 鎖定兩條程序觸發行、
   記錄程序與改進任務程序的必要句，以及共同基線新行的三個片段；F3 檢查 README 目錄樹列出的新檔案；測試的預期清單
   獨立於守衛設定。
7. **D7 本任務照新規則跑**：Skill 驗收後，主代理在 ToukaDev 本機的 `.toukadev/lessons/` 用新格式寫第一批紀錄：1 筆待處理
   （暫存資料夾含 git repo 時，Windows 上 `shutil.rmtree` 因唯讀檔刪不掉），以及 4 筆已處理的源頭紀錄（對應背景中的
   ADR-034、ADR-035 與 PR #6）。後 4 筆是依人類先前已作的決定事後補登，狀態由本任務設定，屬一次性例外；這個例外
   不寫進記錄程序。

## 不變的部分

13 個步驟與全部審核點、5 種審核模式、授權規則、進度網頁與暫存清理規則都不變。記錄不是新的步驟或審核點；
改進任務是一般 dev-workflow 任務。

## 後果

- 流程問題有固定的位置與格式，改進時看得到次數與跨專案的證據，不必靠人類記得。
- 共同基線多一行；新專案範本與 examples 同步。
- 第一次改進任務另行核准，先處理上述待處理紀錄（人類決定唯讀缺口下一批修）。
- 本批合併後，在 ToukaDev repo 工作時就會照新規則記錄；在 Touka 工作時還不會，要另外做三件事（另行核准）：
  Touka 的 `AGENTS.md` 加上這一行（Touka 規則修改，需人類同意）；Touka 的 `scripts/guard_adr_integrity.py` 掃描時
  略過 `.toukadev`，避免紀錄裡寫到的 ADR 編號讓 Touka 守衛失敗；重新安裝 Skills。
- 已安裝的 Skills（例如 `~/.codex/skills`）要重新安裝才會用到新規則，不在本次核准內。
- 已知限制：
  - 守衛只證明有限的文字契約，不證明 agent 該記錄時真的會記錄；漏記只能靠人類回饋發現（那也會被記成反覆困擾）。
  - 「同一根因」靠 AI 判斷，可能重複或誤併；不確定時新增一筆，由改進任務合併。
  - 紀錄只在本機，換電腦或刪掉 `.toukadev/` 就會遺失。
  - 文字鎖只鎖指定的句子與 AGENTS 那一項本身；在旁邊另加段落或清單項寫例外，守衛與測試都擋不到，要靠 DEV-B
    把關。修改「受保護規則的處理方式」本身也屬於受保護的規則，必須在一頁計畫中單獨列出。
