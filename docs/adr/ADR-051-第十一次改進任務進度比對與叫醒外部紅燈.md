## 背景

這是依 ADR-036 進行的第十一次改進任務。人類問進度與路線圖是不是常常沒跟上，評估後選了現在就做「自動比對」的前兩步：先只偵測、再自動填固定欄位；第三步（總覽與路線圖從任務紀錄產生）留到之後的 ToukaDev 改進。

來源是 5 筆待處理紀錄，都在同一個下游專案（另外三處沒有待處理），根因各不相同，各自一組。只讀各專案的 `.toukadev/lessons/`；紀錄是證據，不是授權。一頁計畫經非作者的 DEV-A 3 輪（第 1 輪 CHANGES_REQUIRED：3 個 HIGH、9 個 MEDIUM；第 2 輪 CHANGES_REQUIRED：1 個 HIGH、7 個 MEDIUM；第 3 輪 PASS_WITH_NOTES：2 個 MEDIUM）。第 3 輪剩下的一個 MEDIUM 和前兩輪同一類（沒有網址的列可能被自動改錯），兩輪自動修正已用完，把審查建議的保守做法寫進計畫交人類核准：自動改只限有完整網址、屬於本專案、分支一致的列。

## 教訓

| 紀錄的教訓（概括） | 類型與次數 | 處理 |
|---|---|---|
| 已合併的工作、等人類刪的分支，紀錄還寫進行中或使用中；路線圖也沒跟上，人類問了才發現 | 反覆困擾 1 | D1、D2 |
| 合併或檢查通過時沒人被叫醒；以為宿主會通知，其實它只在失敗時通知 | 重大錯誤 4（處理後又發生） | D3 |
| 攻擊型紅燈測試用絕對路徑，修補前把檔案寫到沙盒外 | 重大錯誤 2（處理後又發生） | D4 |
| 外部安全公告讓依賴掃描變紅，同一天有的帶著紅燈合併、有的等 | 反覆困擾 1 | D5 |
| 新測試改了同檔共用的假資料沒還原，換了執行順序才紅，合併後才發現 | 重大錯誤 2 | D6 |

和已處理紀錄同根因的有兩組：D3 的前一次（第三次改進任務）要求寫明誰用什麼叫醒，沒擋住「把沒實測的方式當成確定會送達」，也沒提到開了自動合併的情況；D4 的前一次（ADR-041 D11）的誘餌目錄只擋相對路徑的穿越。

## 決定

編號和一頁計畫的條次相同。

1. **D1 進度紀錄自動比對實際狀態**（第 1 條）：
   - 網頁不連網就能判斷的：進行中的紀錄，工作清單至少一列且都完成、暫存都已清理或保留時，提示「可能可以標已結束」（不是格式警告）。
   - 新狀態「已移出」：工作搬到另一份紀錄繼續時用，備註開頭寫「移到 <任務代號>」，否則出格式警告（七類變八類）；中性顯示、「完成 x／y」的 x、y 都不算。寫在狀態定義那段，不另寫例外。
   - 新的唯讀比對程式 `sync_progress.py`：以「工作分支」欄認 PR，查到剛好一個、不是 fork、分支一致（有網址時就是網址那個）才比對；已經是完成狀態的列不查（不可能對不上）。遠端分支用 `git ls-remote` 讀目前的 commit，「可以刪」和現行刪遠端分支第 4 種清理項目的前三個條件相同（不是預設或共用分支、PR 已合併、目前的 commit 等於合併時的 head）；工作資料夾要 git 清單和磁碟都沒有才算不存在；本機分支只偵測；寫已清理但其實還在的也報（只偵測）。只用唯讀指令，有時限、關掉登入提示；查不到和不存在分開。
   - 結果寫進 `sync-status.json`，網頁在總覽最上面顯示；讀之前檢查格式與大小、連結略過、文字一律跳脫且不產生連結；比對之後紀錄有改過就標可能過時。
   - 紀錄寫法補兩句：開 PR 時那一列寫完整 PR 網址、工作分支欄寫 PR 的分支；遠端分支的位置寫 `<遠端>/<分支>`。合併後被叫醒時、任務結束前、向人類回報前各跑一次比對。
2. **D2 合併後自動填固定欄位**（第 2 條，放寬，人類單獨接受）：只有主代理能用 `--apply --task <自己的任務代號>`，一次只改一份紀錄的三種固定欄位（工作清單的已合併、遠端分支的保留或已清理、工作資料夾的已清理），並在審核紀錄加一列。工作清單只改有完整網址、PR 屬於本專案、分支一致的列；遠端分支只改位置欄寫明、而且同一份紀錄有這個分支屬於那個遠端的 PR 網址的列；工作資料夾只改上一層資料夾還在的列。寫入前核對要改的那一行就是比對時的那一列、新舊內容只差目標格子與新加的一列，讀檔後被改過就放棄，保留編碼、換行與權限，連結與特殊換行字元拒絕。臨時寫的程式照舊不准改紀錄。
3. **D3 叫醒**（第 3 條）：
   - 「確定會送達的宿主通知」要實測過或有宿主文件；只在失敗時通知的，不能當成成功或合併的叫醒方式。
   - 開自動合併前核對合併條件（CI 全綠、沒有衝突、沒有未處理的審查留言、head 等於審過的 commit）並綁定審過的 head；之後等合併結果，醒來確認再更新紀錄。只改 `supervisor-delegation.md`，因為一個主代理自己合併時讀不到 `team-roles.md`；各工具實際怎麼叫醒不寫進 repo（ADR-040 D1）。
   - 背景等待（放寬，人類單獨接受）：宿主說明寫不要自己輪詢 CI。人類決定把一次、有時限、跑完就結束的背景等待歸在「宿主不鼓勵、但經人類同意可用」，每個任務的一頁計畫寫明、人類核准才用；理由是宿主只在失敗時通知，成功與合併時不等就沒人接手。
4. **D4 攻擊型紅燈測試**（第 4 條）：原句保留，加上輸入含絕對路徑、磁碟代號或連結時誘餌目錄擋不住：測試值直接指向沙盒內，並在測試裡攔下沙盒外的寫入、刪除與搬移，再跑紅燈；變更摘要寫明怎麼攔的。
5. **D5 外部原因的紅燈**（第 5 條，受保護的規則，不放寬）：審核協議 7.2 在 `HUMAN_OVERRIDE` 那句後面（不可弱化區塊外）補明：失敗原因在這個改動之外時同樣不能通過，人類只決定先後（先插隊修掉，或等），不能放行。依 ADR-002 D7，確定性的檢查連人類也不能放行；下游專案先前一次的放行只算那一次。降低等待的做法（把那幾道檢查放進 CI、在守衛裡放一份人類核准且會到期的已知例外清單）是下游專案自己的事，不在這次做。
6. **D6 測試之間的共用狀態**（第 6 條）：用到同檔其他測試也用的假資料或模組狀態時，在用到之前重設；改到時用 `afterEach` 或 `finally` 還原；開了隨機順序的專案，改到的測試檔與故意改壞至少換 5 個種子各跑一次。
7. **D7 減法**（第 7 條）：第 1 版提的「拿掉總覽板可能過期的提示」撤回（每次產生網頁都會出現、也看得到其他專案，D1 的比對取代不了它）；過期變色仍要抓 D1 抓不到的「忘了更新」，留著。這次沒有其他有證據、值得減的規則或程式。
8. **D8 完成後不再跑改進**（第 8 條）。

## 和計畫的差異

實跑與 DEV-B 第 1、2 輪後和核准的計畫不同的地方。鬆緊以「會不會讓紀錄被改錯、或讓該報的沒報」判斷；DEV-B 一欄只寫和作者不同的盲標。

| 項目 | 計畫 | 實作 | 鬆緊（作者） | DEV-B 盲標不同處 |
|---|---|---|---|---|
| PR 網址從哪裡讀 | 那一列唯一的完整 PR 網址 | 只從備註讀；網址寫在其他欄的列當成沒有網址（只偵測）。本機分支也會改看項目欄，只偵測 | 自動改加嚴、偵測略寬 | 外部審查指出這項原本沒列 |
| 工作清單不查的列 | 只有「待辦又沒網址」不報 | 已合併、已完成、已驗收、已移出的列不查；查到 0 個 PR 又沒網址也不報 | 不變（這些列不會對不上，只少了「沒比對」的提示；實跑從 300 多列降到 12 列） | 外部審查：只影響報告的輕微放寬 |
| 只寫分支名的遠端分支 | 專案剛好一個遠端就比對 | 另外要是這份紀錄工作清單用到的分支 | 偵測少一點、自動改加嚴（避免把「位置：GitHub」這類寫法當成分支名而誤報） | — |

| 遠端分支的自動改 | PR 已合併、commit 相同就改 | 還要位置欄寫明，而且同一份紀錄有這個分支屬於那個遠端的 PR 網址；網址指向別的 repo 寫「沒比對」 | 加嚴 | — |

| 工作資料夾的根 | 相對路徑從 `git rev-parse --git-common-dir` 的上一層算 | 改用 `git worktree list` 的第一筆 | 更正（一般 repo 兩者相同；子模組等 common dir 不在專案裡時才不同） | 外部審查建議和下一列分開寫 |
| 工作資料夾的判讀 | 沒寫 | 位置只認路徑（網址、網路路徑、含空白或全形字的不碰）；上一層資料夾還在才自動改 | 加嚴 | — |

## 守衛與測試

沒有改、刪或新增鎖定句，守衛程式沒動。`tests/test_render_progress.py` 加提示、「已移出」與顯示比對結果的測試；新檔 `tests/test_sync_progress.py` 用假的 git／gh 執行器（不連網、不碰真的 repo）鎖住每種比對、`--apply` 只改目標格子、讀檔後被改過就放棄、保留編碼與換行、連結拒絕、結果檔被網頁接受；文件結構測試的 progress 資產清單加上新程式。連結相關的案例在不能建立 symlink 的 Windows 上跳過，由 CI（ubuntu）執行。D3～D6 是判斷類的文字規則，沒有程式行為要測。

DEV-B 由兩位審查者各自進行：新上下文的子代理，以及另一個執行環境的外部審查（同型號）。第 1 輪兩位都是 PASS_WITH_NOTES，HIGH 0；MEDIUM 共 7 項（子代理 3、外部審查 4）：工作資料夾的位置判讀太寬會被自動改成已清理、登記成別的 repo 的遠端分支會被誤改、列號對應沒有回歸測試、`--apply` 沒核對要改的就是比對的那一列、「可以刪」沒排除共用分支、從項目欄認出的遠端分支也會被自動改、本 ADR 沒記偏差。作者查證後全部接受並修正，每項各加會擋住回歸的測試（含改錯列要拒絕、各種難解析的表格寫法與解析結果對照），再送原審查者複審。

第 2 輪兩位仍是 PASS_WITH_NOTES，HIGH 0，第 1 輪的 7 項 MEDIUM 都確認解決。新的一項兩位都提到：第 1 輪加的 ssh 不問密碼會蓋掉使用者的 `core.sshCommand` 與 `GIT_SSH`（外部審查列 MEDIUM、子代理列 LOW），後果是那些遠端全變「查不到」，不會寫錯紀錄。作者接受並修正；同時處理幾項 LOW：預設分支本機沒有時問遠端、表格在圍欄裡時不改、紀錄份數改之前就檢查、寫結果檔失敗時照樣列出已改的列、已清理的列不因別的 repo 網址列成「沒比對」、遠端不是 GitHub 時訊息照實、repo 名稱不分大小寫、原始碼裡看不見的換行字元改成跳脫寫法、說明文字同步，每項各加測試。沒處理的 LOW：網頁的格式錯誤只顯示類別名稱（保守，維持）、審核步驟被改成「已合併」與工作資料夾名稱打錯（寫進已知限制）。這一段修正交子代理覆核（第 3 輪）：PASS_WITH_NOTES，各項都確認解決，HIGH、MEDIUM 0。它提的 LOW 中，作者再處理三項並各加測試：查不到預設分支改列「查不到」，而且只在其他條件都符合時才查；補上工作清單表格在圍欄裡的測試；資料夾讀不到時照常回報、不印出程式錯誤。第 4 輪 PASS_WITH_NOTES，HIGH、MEDIUM 0；剩下的 LOW 再處理：遠端沒有回報預設分支時也當成查不到、測試直接鎖住會被自動改的列仍受預設分支保護、行數更正。最後這段交子代理確認，結果記在 PR 說明。另一項（Windows 上經 git 內建 shell 找到的 ssh 可能和直接找的不同，後果只是「查不到」）記為觀察。

## 行數

## 後果

- 合併後一跑比對，網頁最上面就列出紀錄和實際不一樣的地方；主代理可以用 `--apply` 補上固定欄位，不靠記得。
- 已知限制：
  - 抓不到沒照新寫法的舊列，也不看路線圖；工作搬走後原列沒關的，靠「已移出」避免，比對抓不到。
  - 比對要另外跑；網頁照舊不連網，只顯示上次比對的結果並標可能過時。
  - `--apply` 最後一次核對到替換之間仍有極短的空檔，和刪除程式同樣接受。
  - 帶工作分支與 PR 網址的審核步驟（例如 DEV-B 那一列）也會被改成「已合併」，不是「已完成」。
  - 專案有兩個以上 GitHub 遠端時，沒寫 PR 網址的工作清單列都只能寫「沒比對」；本機分支若登記的是別的 repo 的分支會誤報（只偵測，不自動改）。
  - 「已移出」不檢查那份紀錄在不在。
  - 工作資料夾的名稱打錯、但上一層資料夾存在時，`--apply` 會把它改成「已清理」。
  - 背景等待的歸類是人類對宿主說明的決定，宿主說明改了要重新評估。
- 改動要重新安裝 dev-workflow Skill 才生效；人類已同意本次合併後重裝。
