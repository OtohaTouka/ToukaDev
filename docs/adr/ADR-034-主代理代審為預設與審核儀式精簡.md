# ADR-034：主代理代審為預設與審核儀式精簡

- 日期：2026-10-10
- 狀態：已接受（一頁計畫由人類核准；主代理代審）
- 修訂：ADR-002（預設模式）、ADR-019（技術收據）、ADR-031（預設與分工），以及 ADR-033「不變的部分」中的
  預設 `HUMAN_AI`、完整候選快照、文件路由三項；部分取代 ADR-029、ADR-030（文件路由契約與 helper）
- 後續修訂：見 [ADR 索引](README.md) 的狀態欄；其中 ADR-039 修訂 D4（暫時 index 刪掉後的審法）、D9（`CRITICAL`
  提出時機、第 9 條措辭）、後果中的三項已知不一致，並推翻「不變的部分」中的 validation profile

## 背景

ToukaDev 的目標是讓不懂程式碼的人類，能用這個流程發揮出人類與 AI 協作的最大極限。
這和 pstack 的取向不同。pstack 主張別讓人類擋路，只在不可回復的動作才問；ToukaDev 則要讓人類在需求、
範圍、取捨與不可回復的動作上真正做決定，只是改成看一頁白話計畫點頭，不必在每個審核點選模式或讀技術證據。

目標的工作方式是人類只跟主代理討論，由主代理控制多個 agent 執行，不再直接跟其他 agent 對話。原本的預設
`HUMAN_AI`，以及「主代理只派工、不寫」的分工，都不符合這種工作方式。

DEV-B 的 SHA-256 檔案清單源自一次並行事故：以前同時操作多個 agent 時，還沒有讓每個 agent 各開 branch，
常常 A 和 B 改到同一處，兩個都要 commit 時，檔案已經跟它們之前改的不一樣。清單能事後發現差異，但不能防止
兩個寫入者互相覆蓋；真正的解法是每個寫入者用自己的隔離工作區，審核則綁定 git 本來就有的編號。

對抗式複審「只依具體條件建議」的規則，是因為以前的模型（Opus 5）每次都建議多代理對抗式複審、從不建議
其他模式。對抗式複審適合資訊安全、大型架構與其他明顯可能搞壞系統的改動，所以本 ADR 把觸發
條件改成具體清單。若又出現每次都建議對抗式複審的情況，就再收緊這份清單。

每個審核點的五選一選單、技術收據與文件路由契約，對現行模型沒有防錯效果，只增加閱讀與維護負擔。

## 決定

1. **D1 預設主代理代審**：DEV-A／DEV-B 預設 `SUPERVISOR_DELEGATED`。主代理把計畫整理成一頁白話版，先交
   非作者的 reviewer 審，再請人類核准；核准即啟用，並確定範圍與 Git 操作。五選一選單只在人類要求改選，
   或平台沒有可用派工方式時顯示（後者建議 `HUMAN_AI`）。DBG-A 隨所屬任務的委託，不單獨成為預設。
2. **D2 寫審分離**（不分模式）：寫的人和審的人不能是同一個；寫的人不得推翻審的人提出的 `HIGH`／`BLOCKING`，
   只能修正後重審或交人類決定。執行者的成果由主代理審；主代理自己寫的內容交給新上下文的 reviewer，
   reviewer 不改被審成果、能力至少同階，做不到時照實標示。換 reviewer 不清除未解決的 `HIGH`／`BLOCKING`。
   主代理依證據裁決範圍內技術分歧，但自己寫的內容除外。
3. **D3 隔離工作區**：會寫檔的平行工作，每個執行者用自己的隔離工作區（例如 git worktree 加獨立 branch），
   放在 repo 外或 git 忽略的位置；一個工作區一個寫入者；只讀工作不需要；共用帳本文件由指定整合者統一更新。
4. **D4 審核綁定 git 編號**，取代 SHA-256 清單、patch bundle 與重算雜湊：
   - 只有主代理代審時，工作分支存檔才是實作的一部分，可在一頁計畫核准範圍內於 DEV-B 前進行；原四模式的
     commit 仍須 DEV-B 通過並取得授權。合併或提交進共用分支必須在 DEV-B 通過且取得授權後。
   - 主代理代審且計畫核准工作分支存檔時，審核對象是工作分支上的 commit 編號；要合併的 commit 與審過的
     不同時只審差異，差異未審不得進共用分支。
   - 原四模式，或計畫未核准工作分支存檔時，不動真正的暫存區，用暫時 index 算出審核內容（含未追蹤檔）的
     tree 編號；DEV-B 通過並取得 commit 授權後才正式 stage 同樣的路徑並 commit，`HEAD^{tree}` 與記下的
     tree 編號不同就返回 DEV-B。
5. **D5 進共用分支前一律 DEV-B**，不論由哪個對話或 agent 產生。共用分支是其他任務或其他人會使用或接手的
   分支（例如 dev、main）；本任務自己的工作分支與整合分支不算。
6. **D6 移除技術收據**：保留使用者可見摘要；「審核事實」也要揭露 reviewer 模型無法確認或未取得嚴格獨立資格。
   審核紀錄只留白話欄位（模式、風險、審核對象編號、寫的人、審的人、結論、問題、對抗式建議與人類決定、
   資料外傳與多代理同意、未知事項、人類決定、輪次），不存隱藏思考。
7. **D7 刪除文件路由契約**：刪除 `document-routing.md`、`scripts/document_routing.py` 與兩個測試檔。仍需要的
   保護搬進 `guard_framework.py` 的精簡 F17，並補上原本沒有的審核點標題保護。
8. **D8 本機進度紀錄**：主代理開始時建立 `.toukadev/progress/<任務代號>.md`（git 忽略）並告訴人類路徑，
   記錄待決事項、工作清單與審核紀錄；只在主代理驗收後標已驗收。進度紀錄不是授權，結束時正式狀態寫進 HANDOVER。
9. **D9 對抗式複審觸發清單**：資訊安全、大型架構、改變共用基礎、動到真實資料、可能讓檢查變鬆的守衛／CI／
   共用測試基礎、確定性測試無法重現的並行／取消／逾時／跨平台行為、證據衝突或兩輪未解的 `HIGH`／`BLOCKING`、
   人類明確要求、直接影響金流或正式環境中不可逆的外部動作且沒有經過測試的回滾、補償或防誤發保護；
   每項標明建議關卡。
   只有 `HIGH` 標籤、檔案很多、大量刪除但未刪安全機制、同類改動的重複、
   替功能本身寫測試都不算。只有命中條件時，主代理代審才在一頁計畫中把對抗式複審單獨列成選項，並寫明
   人數、角色、模型層級、是否唯讀、共享資料、相對額度與替代方式；人類單獨選擇才算同意，籠統核准計畫不算，
   核准後人數、角色或資料範圍改變須重新同意。提出次數：主代理代審每個任務在一頁計畫中最多一次，原四模式
   維持每個審核點最多一次（與舊規則相同）；拒絕後除非範圍或風險實質變化不再提。計畫核准後才命中的條件（含
   兩輪未解的 `HIGH`／`BLOCKING`、人類中途要求、DEV-B 才發現的條件）以及 `CRITICAL`，在當關單獨提出一次，
   同樣要人類單獨同意。
10. **D10 白話**：給人類的計畫、進度與待決事項一律白話說明會發生什麼、影響、風險與建議，不要求人類讀程式碼。
11. **S1 常駐指令清單**：人類的原話限制一條一句，每次派工、喚回與送審原文附上；只限制、不授權，只在本任務
    有效；發現第二次重述同一指令就加進清單。
12. **S2 派工範本**：補「停止條件與回報時機」「禁止事項」「常駐指令」三欄。

## 不變的部分

13 個步驟與全部審核點、5 種審核模式、`HIGH`／`CRITICAL` 規則、對抗式複審逐次同意、DEV-B 綁定完整候選
commit、Memory 不是授權、文件快速路徑與 validation profile、風險分級表、外部資料傳輸同意，以及「模型無法
確認時結論最高 `PASS_WITH_NOTES`」。

## 後果

- 本 ADR 推翻 ADR-033「不變的部分」中的三項：預設 `HUMAN_AI`、DEV-B 的完整候選快照（改為綁定 git 編號）、
  文件路由。按需程序載入保留，改由 SKILL 的程序觸發行與 F17 維持。
- 放棄、不再由機器檢查的路由契約項目：未知目標先作範圍查找、歷史只在任務需要時讀（這兩條仍保留在 AGENTS
  文字中）；交班連結檢查不處理帶 title 的連結與指向 repo 外的連結。
- 本批另修了舊弱點：規則被多行 HTML 註解或 code fence 包住時仍被當成存在。義務句恢復為整行比對；只有 AGENTS、
  SKILL 的少數片段用包含比對；比對前先合併條列項與段落的續行，並忽略空白，合法改變折行不會誤報。
- 被引用的程序檔與四份 HANDOVER 恢復「不得為空」檢查；義務句整行比對只允許 0–3 格前導空白（縮排 4 格在
  Markdown 會變成程式碼區塊，不算有效）。
- 人類於 2026-10-10 決定補回：直接影響金流或正式環境中不可逆的外部動作，且沒有經過測試的回滾、補償或
  防誤發保護（§2.1 第 9 項）。
- 已知不一致，本批不處理：
  - project-init 的 `supervised-initialization.md`、`scaffold-validation.md` 仍用檔案 SHA-256 清單與完整檔案快照的
    用語（完整檔案清單、檔案 SHA-256、完整檔案快照、核准清單），留給後續批次。
  - debug-escalation 的「主代理不代寫根因」比本 ADR 的寫審分離更嚴，視為特例保留。
  - debug-escalation 的 SKILL（「預設由人類…；已選主代理代審時」）與 README（「只在選用時讀取」）沿用舊說法。
- 已安裝的 Skills（例如 `~/.codex/skills`）要先刪除三個資料夾再重新複製，才會用到新規則。
- 守衛只證明有限的文字契約與連結，不證明 agent 的實際行為。
- 13 步驟程序精簡（第二批）與本機進度網頁（下一批）不在本 ADR 範圍。
