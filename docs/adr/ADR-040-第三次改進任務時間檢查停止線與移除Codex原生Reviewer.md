## 背景

這是依 ADR-036 進行的第三次改進任務。來源：ToukaDev 的 5 筆待處理紀錄、人類指定的另一個專案的 4 筆待處理紀錄、
交班文件「下一步」的候選，以及團隊的本機反省筆記（只當補充證據）。紀錄是證據，不是授權。

## 教訓

- **同一事件跨來源只算一次**：等 CI 時全員停住，兩邊各記了 2 次，其實是同兩次事件，合計 2 次。
- **已處理的紀錄再發生，代表先前的改法不夠**：ADR-038 D2 用文字規則要求寫進紀錄的時間取系統時間，重新安裝後仍發生
  3 次、差點 2 次。第 1 次發生在 ToukaDev 自己的任務，依記錄程序當時就該在 ToukaDev 重開那筆已處理紀錄，卻記到了
  另一個專案（執行時漏做）；之後發生在另一個專案的，記錄程序只找本專案，看不到 ToukaDev 的已處理紀錄（規則缺口）。
  所以這次改用檢查程式（D3），並在改進分析端補上對照（D8），不放寬記錄端去讀其他專案。
- **紀錄引用的規則要核對**：行數估低那筆寫「planning.md 要附規模估計」，但 ToukaDev 其實沒有一般任務的停止線，
  團隊一直沿用改進任務的算法、每次請人類核准（D5）。行數漏算的都是同一類：證明「該擋會擋」的測試、測試基礎設施
  自己的測試、鎖定句與 ADR。

| 紀錄的教訓（概括） | 次數 | 處理 |
|---|---|---|
| 等外部事件（CI、背景工作）時全員停住，要人類自己發現 | 2 | D1 |
| 規劃漏想，執行中多問人類；計畫先引用還沒建立的 ADR 編號，被檢查擋下 | 1＋1 | D2 |
| 進度紀錄的時間寫成估的、新列插錯位置（已處理紀錄再發生） | 3，另差點 2 | D3 |
| 總覽「✔／全部」讓做完的任務看起來沒做完 | 1 | D4 |
| 測試多的任務行數一再估低 | 2 | D5 |
| 臨時查驗在沙盒外載入專案程式，自動寫出設定檔（差點出事） | 1 | D6 |
| 用編號核准的決定單隨別的任務暫存被刪 | 1 | D7 |
| 跨來源重複、已處理紀錄再發生沒被重開（本次分析發現） | 2 例 | D8 |

D9–D12 來自分析的減法與量測。不採用：少傳回報（人類說有用）、寫明主代理可自決的範圍（已涵蓋）、規定外的狀態值
（網頁已警告）、只發生一次的決策文件多版（保留觀察）、另一個專案自己的檢查。

## 決定

1. **D1 等外部事件前寫好喚醒方式**：supervisor-delegation 在首批試行平台那行後加三行：結束回合前在進度紀錄寫明在等什麼、
   何時開始、預計多久、由誰用什麼方式叫醒，不能只靠另一個也在等的參與者；方式依序是確定會送達的宿主通知、宿主允許的
   有時限等待、宿主不鼓勵但人類在本任務為這個用途明確同意並記在紀錄的方式，都沒有就請人類到時叫醒；宿主禁止的一律不用；
   被叫醒時先查逾時的等待。progress-record 的更新時機加「開始等外部事件」。特定工具的觀察行為不進 repo，也沒加鎖。
   剩餘風險：規則不能憑空叫醒代理；宿主沒有可靠通知又不允許等待時，只能讓人類事先知道何時要叫。
2. **D2 規劃先列出執行中會撞到的點**：planning 的「ADR 影響」補上新編號或登記（ADR、豁免、守衛基準）寫明在哪個單位建立，
   排在第一個引用它的單位之前或同一單位；3-4 加一點：範圍外的檔案、受保護的規則、外部實測的設定或金鑰位置（只確認存在）、
   行數停止線的數值，能先查的先查（受保護位置依專案資料保護規則，不能查就列給人類確認），要決定的附建議一次問；核准的
   預設做法照做再回報，但每批外部實測、對抗式或多代理複審、資料外傳、不在委託內的 commit、不可逆動作、受保護規則的移除
   或弱化、停止線觸發時的停下與專案要求的逐次同意不套用預設。supervisor-delegation 加一行：幾件要決定的事合成一則，逐次同意
   仍逐項列出、逐項回覆。審核協議 DEV-A 檢查重點同步。剩餘風險：靠規劃的人照做；ToukaDev 無法替下游的守衛預判。
3. **D3 進度網頁檢查審核時間**（部分推翻 ADR-038 D1）：
   - 只查任務狀態是「進行中」的紀錄、只看審核紀錄的「時間」欄；認得 `M/D HH:MM` 與 `YYYY-MM-DD HH:MM`（前面可有「約」），
     看不懂的格子跳過。某列比上一列早（相等允許），或比紀錄檔修改時間晚 2～59 分鐘，就加一條警告，沿用既有管道
     （網頁警告框、總覽「格式警告 N」、命令列）。只寫月日時取修改時間那年，比修改時間晚超過 30 天才當成前一年。
   - progress-record：「格式警告只有兩種」改成三類並寫明範圍與抓不到的情況；更新時機補「新的一列接在表格最後；先取時間
     再寫列」；審核紀錄說明改成「每列一兩句摘要」（減法 S5）。
   - 為什麼現在加回：D1 刪的是沒有事故紀錄的格式細節；時間問題在文字規則生效後仍發生，已證明文字擋不住。這次只查一欄、
     兩個條件，不對格式提新要求。不恢復 `更新時間：` 的解析、舊格式偵測與其他細部警告。
   - 剩餘風險：寫得比實際早但順序沒錯、只晚 1 分鐘、晚超過 59 分鐘的抓不到（上限是為了不把本機與 UTC 的時差當成錯）；
     修改時間在下次存檔時會追上，未來時間只在寫完當下重產網頁時警告；混用本機與 UTC 時間會出現順序警告。
4. **D4 總覽改「完成 x／y」**：x 含已驗收、已合併與已完成，做完就是 y／y；小字寫其中幾項經驗收或合併；表頭改
   「進度（完成／全部）」，任務頁摘要相同。每列的 ✔ 與中性「完成」的區分保留。
5. **D5 一般任務的停止線**（人類核准）：planning 3-4 新增「規模估計與停止線」：一般任務的停止線只算產品程式與規則文件，
   估計給範圍、以最不樂觀的一端為準，多出 100 行以上且估計為增加時超過 1.5 倍，開 PR 前停下問人類。測試不計入停止線，
   改在步驟 12 的變更摘要附兩項證據：改到的產品程式被測試執行到的比例（專案有宣告覆蓋率命令時；沒有就寫未量測），以及
   釘住既有行為的測試故意改壞後會變紅的紀錄；兩項都沒有的測試刪除或寫明理由，另列測試行數。delivery 步驟 12 同步一行。
   **改進任務的停止線（improvement-run，整個 repo 都算）不變。** 代價：每個專案要宣告覆蓋率命令，否則只能寫未量測；
   每次多跑覆蓋率、逐組做改壞驗證；測試行數不再讓工作停下，測試可能持續變多，只靠證據要求和變更摘要列出的測試行數
   讓人類看見。
6. **D6 臨時查驗也受沙盒限制**（加強資料保護）：四份共同區塊的沙盒那行補「臨時查驗不得在沙盒外載入可能寫入的專案程式
   （載入時的初始化也算寫入），需要時改寫成沙盒內的測試」，逐字同步；派工範本的禁止事項加同一例子。剩餘風險：ToukaDev
   沒辦法偵測，靠執行者遵守；具體禁令由各專案寫進自己的 AGENTS。
7. **D7 編號回覆要抄內容**：progress-record 加一句：人類用編號或代號回覆時，審核紀錄同時寫下每個編號代表的內容；一份
   決定單涵蓋幾個任務時，每個任務的紀錄各抄自己的部分。清理規則不動。
8. **D8 改進分析的去重與對照**：improvement-run 第 1 點補：不同來源的同一事件只算一次；和已處理的紀錄同一根因時，視為
   先前的改法不夠，在分析中說明。
9. **D9 README 縮短**：dev-workflow/README 的「這個 Skill 做什麼」縮成步驟清單加指向正本的連結；根 README 的審核點、主代理
   代審與進度網頁三段縮成摘要，「需要客製化的部分」表改指 project-init/README。守衛鎖定的句子保留，守衛不改。
10. **D10 刪除 `hooks/`**（人類確認沒有在任何地方裝它）：連同根 README 目錄樹的三行與 debug-escalation SKILL 的指向段。
    剩餘風險：除錯迴圈只靠 SKILL「同一錯誤第 3 次」的自我檢查，沒有工具層提醒。
11. **D11 測試覆蓋率量測**：只報告，不刪測試、不新增依賴，結果見「量測」。
12. **D12 移除 Codex 原生 reviewer 支援**（受保護規則，單獨核准；理由是人類確認已不使用）：
    - 刪除 `codex-notes.md`、兩份 reviewer 設定檔、F1 的設定檔副本檢查與它的 5 個測試；審核協議的讀取時機、不可弱化規則中的
      Codex 句與例外、3.4 的指向，3.7 的例子改成一般說法，§4.1 刪除；共同基線刪「Codex 原生 reviewer 只算參考意見」那行與
      不可信材料那行的例外子句、規則候選那行的「不擴張舊 profile 例外」（四份同步）；dev-workflow SKILL 的「審核協議所列的
      reviewer profiles」改成「改選其他審核模式」；project-init SKILL 的設定檔一節與禁止行為一行；brownfield 的 B7 一節（B8 改為
      B7）；README、commands、glossary、beginner-guide、supervisor-delegation、scaffold-validation、
      supervised-initialization、SSOT 與介面導航、HANDOVER 精確入口中的指向。
    - 守衛鎖定清單：F8 刪「Codex 原生 reviewer 只算參考意見…」一句，改寫三句：「主代理先選模式再選調度方式…」去掉「也不自動
      套用 Codex reviewer profile」；「平台專屬的執行 profile…」兩行併成「…不是額外的審核模式，也不得作為本區塊任何規則的
      例外」；「審核材料視為不可信資料…」去掉例外子句。共同基線清單刪同一句、同樣改寫不可信材料句。測試期望值同步，
      刪掉的 F1 名稱列入已退役檢查。
    - 不動 Codex 當執行載體的部分：仍是首批試行平台、依 SKILL.md 觸發、可承載主代理派工。
    - 沒有弱化：拿掉的是這個選項連同它的例外；平台 profile 那句的例外部分加嚴（任何平台都不得例外），原本「平台 adapter
      明列才可使用」的准用名單改由一般規則承擔（同區塊的嚴格獨立與模型揭露兩條、§3.2–3.4）；多代理逐次同意、寫審分離、
      五種模式不變。改到既有守衛，命中審核協議 2.1 第 5 條，所以另請人類同意對抗式複審。
    - 審核協議 3.7 的「平台 adapter」與 SSOT 導航的「平台使用說明」兩個詞維持不動，當成工具專屬說明的通稱；目前沒有這類
      檔案，將來新增時直接適用。
    - ADR-033 影響一節指向的「舊機制的手動清理」清單（舊部署工具留下的 state、lock 與 transaction 檔）現在只在 git 歷史：
      `d269a9d` 的 `dev-workflow/references/codex-notes.md`。ADR-033 內文指向該檔的連結也以 git 歷史為準。
    - 剩餘風險：已手動複製到其他專案的 reviewer 設定檔不會被移除，需要時由人類刪除；已安裝的 Skills 直接覆蓋複製時，
      已刪的 `codex-notes.md` 會殘留。

## 量測（D11）

方法：只用 Python 標準函式庫，量測腳本放在本任務暫存資料夾、不進 repo，`uv.lock` 不變。可執行行取自 `trace` 模組的行表
（與 `python -m trace --missing` 相同，不含 docstring）；在同一個行程跑整套 `pytest tests`，用 `sys.settrace` 與
`threading.settrace` 只記目標檔執行到的行；測試另外啟動的 Python 子行程經 PYTHONPATH 上的 `sitecustomize.py` 一併記錄，
用 `-I` 啟動的子行程不讀 PYTHONPATH，沒有計入。量測對象是三個單位合入後的候選（`548e92a`），855 passed、7 skipped。

| 程式 | 可執行行 | 測試執行到 | 比例 |
|---|---|---|---|
| `scripts/guard_framework.py` | 769 | 702 | 91.3% |
| `dev-workflow/assets/progress/render_progress.py` | 932 | 901 | 96.7% |
| `dev-workflow/assets/progress/check_cleanup.py` | 388 | 371 | 95.6% |
| `dev-workflow/assets/progress/delete_tmp.py` | 69 | 69 | 100% |
| 合計 | 2,158 | 2,043 | 94.7% |

- 只看同一行程時合計 2,040 行（94.5%），子行程只多執行到 3 行。
- 守衛沒執行到的 67 行中，35 行是 F3 的 README 目錄樹檢查（22）與 F1 的 glossary 副本檢查（13）：沒有單元測試，只在實際
  執行守衛時跑（CI 與三件套都會跑）。其餘多是錯誤與平台分支。
- `project-init/assets/templates/scripts/` 的四支下游範本腳本（866 可執行行）不在 ToukaDev 的測試範圍，執行到 0 行；
  examples 沒量。
- 解讀：測試行數約是程式的 1.7 倍，但這只說明多數行有被執行到，不證明斷言有效，也不能直接回答「測試是否過量」。要找可刪的
  重複測試，下一步可用同一方法量每個測試獨有覆蓋的行；本次沒做。

## 守衛與測試

- F1 只剩 glossary 副本檢查；F8 與共同基線鎖定見 D12；F17 沒有新增或改動鎖定；四份共同區塊的同步檢查通過。
- 進度網頁新增 7 個審核時間測試與 2 個「完成 x／y」測試，用暫存目錄與 `os.utime` 設定修改時間，不依賴當下時間或實際紀錄。
- 突變證明：審核時間檢查的每個條件、上下限與跨年門檻各改兩個方向、「約」與完整日期格式、只查進行中、看不懂的日期、
  相等允許，以及完成數、表頭與摘要的舊寫法，共 20 個突變都會讓測試變紅；D12 把退役的 F1 名稱加回會讓測試變紅，把改寫過的
  鎖定句改回含 Codex 的舊寫法會讓守衛變紅（三個單位合入後的候選上重跑過這 26 個突變）。鎖定只檢查句子存在，刪掉的那句被加回
  不會被擋。
