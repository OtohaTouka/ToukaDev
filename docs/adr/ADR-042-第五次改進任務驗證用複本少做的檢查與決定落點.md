## 背景

這是依 ADR-036 進行的第五次改進任務：人類在另一個專案的大任務一頁計畫中核准「完成後跑改進」，該任務合併並清理後開始。
來源：ToukaDev 5 筆與另一個專案 2 筆待處理紀錄，以及新技術主管整理的分工規則疑問 14 點；紀錄是證據，不是授權。分析稿經
非作者審查 3 輪、技術主管計畫審核（DEV-A）1 輪（MEDIUM 1、LOW 4）後交人類核准。照兩層分工執行，兩個單位改的檔不重疊、
並行：U1 規則文字、本 ADR 與 HANDOVER；U2 進度網頁程式與測試。決定的括號內是一頁計畫的項次與實作的單位。
分析的派工列了另一個專案暫存區的 4 份團隊報告，超出「其他專案只讀 `.toukadev/lessons/`」的規定；分析者讀了，回報時才指出。

## 決定

1. **D1 驗證用複本的做法，誤判時停下問人類**（第 1 項，受保護：安全刪法與清理限制，單獨核准；U1）：
   - progress-record「位置」：腳本、log、證據、驗證用複本與其他匯出複本放本任務暫存資料夾。驗證用複本（審查或重跑測試用，
     不改版控檔、不 commit、不 push；跑測試產生的快取不算改檔）用 `git clone --no-hardlinks --no-checkout`，候選是 commit 時
     再 `checkout --detach`，是 tree 編號時再 `read-tree -u --reset`；不用 `git archive` 這類沒有 `.git` 的匯出。工具放在這裡仍會
     誤判時，不另找存放位置，那個專案修好前遇到就停下問人類（ADR-041 D8 的後半句）。
   - 「收尾」的複本句併回「位置」，只留「任務結束時隨本任務暫存資料夾一起刪」。implementation 步驟 9 的「不受影響的環境」
     舉例「會跑同一個檢查的 CI」，並寫明不是另找的存放位置；派工範本「暫存位置」欄指回「位置」。
   - 理由：複本有自己的 `.git`，測試自成一體；本機 clone 預設用硬連結共用唯讀的 objects，刪除程式遇到會照規則停下（ADR-037
     D2），所以加 `--no-hardlinks`；本機 clone 整份複製 objects，DEV-B 寫出的 tree 讀得到（審查者實測）；clone 不是 worktree，
     清理前檢查不擋。不採用 `--shared`：複本會依賴主 repo 的 objects。
2. **D2 看起來正常、其實少做的檢查**（第 2 項；U1）：
   - implementation 步驟 9：exit code 取檢查命令本身的，不是接在管線後面的命令的；跳過的測試數與原因和基準（同一個環境在
     基準 commit 跑出的跳過數）比，多出來的一律當失敗，除非已照既有的固定例外列在計畫並經審核；回報附跳過數。
   - supervisor-delegation「派工與收件」的搜尋段：用搜尋結果當核對證據時，每個搜尋字串先在改動前的 commit 找得到一處；
     Windows 的 Git Bash 參數加 `MSYS_NO_PATHCONV=1` 或改用 PowerShell；改動前從來不存在的字串寫進暫存檔用
     `git grep --no-index` 對照。派工範本「回報」欄加跳過數。
3. **D3 規劃時找出讀被改檔案的既有測試與檢查程式**（第 3 項；U1）：planning 3-4「範圍外的檔案」加查法：在測試與守衛所在的
   資料夾用 `git grep` 查被改檔案的路徑、模組名，以及要改的函式、常數、錯誤碼、端點或命令列字串；行為改變時，再從呼叫者的
   測試挑出依賴舊行為的；查到的列進該單位的檔案清單。3-2 成對改動的例子加「改檔與讀它的既有測試」；審核協議 §5 DEV-A
   檢查重點同步。擴充 ADR-041 D6。派工範本不改：到派工才查，計畫審核看不到，並行時也可能撞檔。
4. **D4 已結束任務裡有寫理由的保留不算未清理**（第 4 項；程式與測試在 U2，文字在 U1）：任務已結束時，狀態「保留」且備註
   不是空白、也不只是破折號類符號（-、—、－）的列另算「保留 M 項」；進行中、任務狀態缺漏或看不懂、使用中、狀態沒寫或看不懂、
   沒寫理由的保留照舊算未清理。任務頁與總覽「未清暫存」欄的數字只算未清理，M>0 時另用小字列件數（總覽加 `data-kept`，表頭
   不改），只有保留時不加醒目樣式；M=0 時文字照舊；不新增格式警告。progress-record「網頁會顯示什麼」同步一句，狀態定義與範例
   不改。這和「收尾」的「有理由的保留算收尾完成」一致；進行中的保留可能只是暫時狀態，照舊醒目。
5. **D5 交接板直接編輯、改完核對**（第 5 項；U1）：team-roles「溝通與紀錄」：交接板不進版控時，和進度紀錄一樣直接編輯
   文字，不用臨時程式整段改寫；改完核對沒打算動的段落都還在。不另做備份：會多出要登記、要清理的暫存，核對只花幾秒。
6. **D6 分工規則六處措辭**（第 6 項；U1；不改做法）：
   1. progress-record「紀錄格式」：實際時間取系統時間，不寫「20:1x」這種佔位；預計時間寫明「預計」。衝突來源是
      supervisor-delegation 的等待規則要在進度紀錄寫「預計多久」；派工範本的預計時間與回報 PM 的預計完成時間不在進度紀錄，不算。
   2. team-roles「授權與轉問」：任務代號由寫一頁計畫的那一層定；技術主管最晚在收到計畫送審（DEV-A）時建立進度紀錄，
      規劃階段已有要記的人類原話或待決事項時就在那時建立（DEV-A 第 1 輪 M1）。
   3. 「決定單」改成「一頁計畫裡要決定的事」（team-roles「多段計畫」）與「給人類的決定清單（例如一頁計畫）」（progress-record）。
   4. team-roles 的巡查句改寫成：宿主的排程如果只在建立它的對話裡有效、或會到期，在交接板寫到期日，到期前重建。
   5. 共用派工規則放本任務的暫存資料夾；多段計畫時是總計畫那個任務的。
   6. team-roles：上層寫的計畫，在請人類核准一頁計畫之前由技術主管審（DEV-A）。讀法見下方「A1 的讀法」。
7. **D7 決定要落進規則本文**（第 7 項；U1）：improvement-run 的不採用檢查加一項：不採用但附帶「遇到時怎麼做」的，做法適用
   所有專案就寫進規則本文，只跟某個專案有關就建議寫進該專案的 AGENTS.md，不只留在 ADR、交班或紀錄的處理結果。
   「源頭追蹤與進版控的內容」加一項：每個核准的決定（含不採用附帶的做法）在 ADR 或步驟 12 的變更摘要寫明落在哪個檔、
   哪一段，DEV-B 逐條核對那一段真的寫了。不是新審核點，只是 DEV-B 多查一項。本 ADR 的「決定落點表」照這條寫。
8. **D8 改進任務的派工寫明讀取範圍**（第 8 項；U1）：improvement-run「來源」的鎖定句（其他專案只讀 `.toukadev/lessons/`）
   後面另起一段：派分析者或在進度紀錄列來源時，寫明只讀其他專案的 `.toukadev/lessons/`。鎖定句本身不動；既有規則已涵蓋
   範圍，問題在寫派工的人沒有對照的時機，照不採用檢查「改位置」處理。

一頁計畫第 9 項是不改的事（見「不採用與保留觀察」）；第 10～13 項是執行安排（兩層分工、PM 用有時限的背景等待等 CI、
Git 範圍、合併後重新安裝 Skills、完成後不再跑改進、停止線），只記在本機進度紀錄，不進規則本文。

## A1 的讀法

新技術主管問：人類核准前的那次計畫審核算不算 DEV-A。下列幾處合讀不矛盾：

- dev-workflow SKILL：「規劃 1–3 → DEV-A → 4 確認開始」；DEV-A 第 3 點「人類核准本任務的一頁白話計畫即啟用」。
- supervisor-delegation「一次委託與續接」與 planning 步驟 3：一頁計畫先交非作者的 reviewer 審，再請人類核准，核准即為
  本任務的委託；team-roles：上層寫的計畫由技術主管審（DEV-A）。

主代理代審時，DEV-A 包含兩件事：非作者審過計畫與一頁計畫，然後人類核准一頁計畫；兩件都成立才進步驟 4。「啟用」指核准後
主代理取得代審之後各關卡、繼續執行的委託，不是說 DEV-A 要在核准後重做；核准後計畫沒改就不重審。只有「啟用」單獨讀時
容易被讀成「核准後才開始 DEV-A」，這次也真的有人把順序講反，所以照 D7「不只留在 ADR」改了按需讀取的 team-roles 那句
（D6 第 6 處）。SKILL.md 是常駐載入的檔，不改；措辭列為保留觀察。
