## 背景

這是依 ADR-036 進行的第四次改進任務。來源：人類要求把團隊分工的角色和規則寫進 ToukaDev、規劃與技術主管兩份反省、
ToukaDev 2 筆與另一個專案 8 筆待處理紀錄、1 項交班待辦（共同區塊的沙盒那行沒鎖），以及人類核准的第 1 項討論稿。
紀錄是證據，不是授權。一頁計畫 16 項由人類逐條回覆，第 1 項先討論再定案，受保護的 P-A、P-B 另外單獨核准。
本任務照兩層分工執行：技術主管做計畫審核（DEV-A），依檔案切成五個單位，檔案不重疊的並行；裁定只加嚴，不擴大授權。
DEV-A 時有兩處核准推定不了（第 1 項其餘五節、第 13 項其他電腦有沒有裝），交人類決定；回覆後兩處都做（D1、D15）。

## 教訓

- **已處理或不採用的紀錄再發生，代表先前的改法不夠**：沙盒外載入在 ADR-040 D6 之後又發生，措辭沒點名間接載入（D9）；
  ADR-037 D3 不採用的清理前檢查問題又發生，規模大得多（同一批 77 個工作資料夾有 61 個被擋），改用檢查程式（D13）。
- **「同一問題最多兩輪」擋不住每輪都不同的來回**：一個區塊修了 6 輪、約 5.5 小時，還有一輪拿掉舊檢查而退步（D5）。

## 決定

括號內是一頁計畫的項次與實作的 commit。

1. **D1 選用的多對話分工**（第 1 項，討論稿 A～D；`b65de9f`、`9877117`）：
   - 新增 `dev-workflow/references/team-roles.md`，人類在一頁計畫選用時才讀，沒選用照 supervisor-delegation 由一個
     主代理做全部；分工是主代理代審的一種調度方式，不是第六種審核模式。內容：適用範圍（兩層是 PM 兼 CTO 加技術主管，
     三層是 CTO、PM、技術主管；人類只跟最上層談）、角色表與四條說明、決定權表（最上面一列是一定要人類同意的事；選用
     分工時合併進預設分支由人類自己做）、派工對照表（偏離只限表格裡的預設值，不得放寬任何現行規則）、改進迴圈。
   - 人類決定後補上（`9877117`）：CTO 加轉問；PM 維護「需要你決定的事」的轉問（兩層時把要決定的事告訴人類，把人類原話
     逐字轉給技術主管），清單本身由技術主管寫，另核對技術主管交回的證據；技術主管是進度紀錄唯一寫入者。授權與轉問六條
     （只有記在進度紀錄、可核對的人類原話算同意；單一寫入者；技術主管不直接問人類；逐字轉達；直接指示照做並逐字記錄；
     本人要回覆的題目沒有預設）；溝通與紀錄、等待與叫醒（額度用完前存檔）、多段計畫（沉默不是同意、跨段 DEV-B）、並行與整合。
   - 每個任務都適用的改在 supervisor-delegation：宿主的可程式化多代理編排只用在本來就要人類逐次同意的多代理工作或
     人類主動要求時；派工範本三欄改寫（命令與每個命令的 exit code、完整失敗清單；基準 commit、預計時間與單位停止線；
     先用自己的話重述問題）；最終回報固定五段。指向：dev-workflow SKILL 觸發行（F17 鎖）、兩份 README、SSOT 導航、HANDOVER。
2. **D2 改進任務也可在大任務的一頁計畫事先核准**（P-A，受保護，單獨核准；`5677fee`）：
   - improvement-run「啟動」的鎖定句改成：人類說要開始，或在大任務的一頁計畫中核准「完成後跑改進」；其他時候照舊只提醒
     一句。新增一段鎖定句：大任務的定義、只對該任務有效、要人類明確回覆（籠統核准整份一頁計畫不算，DEV-A 裁定加嚴）、
     沒回覆、回「不要」或主要任務取消、沒合併都不跑。
   - 沒加鎖的兩段：主要任務合併進共用分支並清理後才開始擬方案；沒有待處理紀錄（交班待辦不單獨算）只回報「這次沒有
     要改的」；改進任務本身也附這一項、每次由人類回答；「啟動」那列引用主要任務一頁計畫中核准的那筆人類原話。recording.md
     不提醒那句補「已核准且會照『啟動』開始時不另提醒」並加鎖；supervisor-delegation、improvement-loop、根 README 與四份
     glossary 同步。
3. **D3 三道防改鬆的檢查**（P-B，受保護，加嚴，單獨核准；`5677fee`）：improvement-run「受保護的規則」加一段並加鎖：
   作者與審的人各自標每條改動「加嚴／不變／放寬」，任一方判放寬就單獨列給人類；計畫審核固定找哪裡變鬆；合併前把改、
   刪或新增的鎖定句逐句對到人類核准的編號。怎麼執行（不進規則本文）：
   1. 作者在分析與一頁計畫每項標記；派給審的人時先不附作者的標記，審的人自己標完再對照。
   2. 計畫審核（DEV-A）的派工固定寫一條「找哪裡變鬆」，含旁邊另加的例外。
   3. DEV-B 列出基準 commit 到候選之間，守衛逐字鎖的句子改了、刪了或新增哪些（比對守衛清單與被鎖文件的差異），
      逐句對到一頁計畫中人類核准的編號；對不上就退回，不自己補核准。
4. **D4 「需要你決定的事」保留編號與選項**（第 2 項；`56297cd`、`c43d724`、`b65de9f`、`12ef5c4`）：progress-record 與
   範例改成編號清單，一件一項（要決定什麼、建議、不決定的影響、沒回覆時怎麼做），選項寫成縮排的子項目，編號不重用；
   沒回覆只照核准過的預設做，沒有預設或屬於 planning 3-4 不套用預設的事就暫停那部分。supervisor-delegation：要決定的事
   加進這份清單，擋住全部工作的另在對話提一句。`render_progress.py`：編號清單輸出 `<ol>`，每個 `<li>` 用 `value` 保留
   原號；比上一項多縮排 2 格以上的條列掛成一層子清單；件數只算最上層；有子項目的不算「目前沒有」；`-` 條列與跳脫照舊。
5. **D5 同一行為第二次 HIGH 算不收斂**（第 3 項；`b65de9f`、`c43d724`）：同一個需求或判定規則在實作或 DEV-B 第二次出現
   HIGH，即使是不同問題，也停止逐條修，依 debug-escalation 寫根因、一句話規則與判定表，經 DBG-A 再修；修正只加檢查，
   要拿掉或放寬既有檢查要寫理由交審的人。debug-escalation 觸發句同步；implementation 步驟 5 加條件組合用對照表測試。
6. **D6 成對改動放同一單位**（第 4 項；`c43d724`）：planning 3-2 補「少一半就會讓檢查失敗的成對改動放在同一個單位」，
   DEV-A 檢查重點同步；擴充 ADR-040 D2 只涵蓋新編號的範圍。
7. **D7 並行時暫存與驗收隔離**（第 5 項；`b65de9f`、`c43d724`）：並行單位各用 `.toukadev/tmp/<任務代號>/<單位>/`；宿主
   暫存區照宿主規則用、照單位分，並照樣登記（類型「其他」、狀態「保留」、備註「宿主管理」；DEV-A 裁定，暫存位置的
   鎖定句不開例外）；驗收期間也不在同一工作資料夾寫入或派工，補件等驗收結束或換資料夾做。
8. **D8 判綠看 exit code 與完整失敗清單**（第 6 項；`b65de9f`、`c43d724`）：implementation 步驟 9 與派工範本：不截斷輸出，
   回報附命令、exit code、最後一行、資料夾與 commit；環境造成的固定例外要列在計畫並經審核，每次判綠在同一個 commit
   於不受影響的環境重跑通過。不另開存放例外：放進暫存位置仍會誤判的工具，那個專案修好前遇到就停下問人類。
9. **D9 臨時查驗與搜尋**（第 7 項；`bfaf3c0`、`b65de9f`）：四份共同區塊的沙盒那行括號補「含經腳本或測試模組間接載入」，
   派工範本同步並禁止在 repo 根或 `.toukadev/` 遞迴搜尋；搜尋用 `git grep`（受保護的被追蹤檔用 pathspec 排除）或指定
   子目錄，禁止讀取的位置搜尋也算讀取，不小心讀到時回報位置、不抄內容。
10. **D10 共同區塊沙盒那行加鎖**（第 8 項，交班待辦；`bfaf3c0`）：F6 的品質義務清單鎖住改寫後的整行，測試同 commit。
11. **D11 攻擊型紅測試先確認寫入目標**（第 9 項；`c43d724`）：會寫檔或測路徑穿越的紅測試修改前就會真的執行，先確認
    寫入目標在沙盒內（例如放一層誘餌上層目錄），突變一次只拿掉一道防線。
12. **D12 單位合入後就清它的工作資料夾**（第 10 項；`c43d724`）：分支等任務分支合進共用分支後再清；`git branch -d`
    只刪已合併的分支（設了 upstream 時比對 upstream），本機共用分支只用 fast-forward 更新，不能就問人類；reviewer 的
    匯出複本放本任務暫存資料夾、隨它刪。刪法與檢查不變。
13. **D13 清理前檢查認得宣告的建置產物**（第 11 項，受保護，單獨核准；宣告位置在複驗後由人類改選純文字檔；
    `536a9b5`、`c43d724`、`6d614f0`、`bab4f20`、`9c32357`、`1fa0333`）：
    - 專案在 repo 根目錄放 `rebuildable-outputs.txt`（UTF-8 一般檔，symlink 等就整份不採用），每行只能是空行（不能含空白）
      或一個從 repo 根算起的相對路徑，不能有註解、清單符號或反引號；開頭的 BOM 與行尾的 `\r` 去掉；任何一行不合法就整份
      不採用。沒有檔（或空檔、只有空行）就是沒有宣告，也不印附註。宣告的新增或修改要列進該任務的一頁計畫給人類核准。
    - 只用 `git cat-file` 從本機 `origin/HEAD` 指到的 `refs/remotes/origin/*` 分支讀（先釘住 commit），不退回 main／dev、
      目前分支或工作資料夾裡的檔；有這個檔而 `origin/HEAD` 和已登記連結工作資料夾的分支同名時不採用。真的靠宣告放行時
      才印「已採用宣告（ref @ commit）」，不採用時印原因與哪一行；附註前加「附註：」。程式本身不 fetch：輸出有「已採用宣告」時，規則要求清理前
      先 `git fetch origin` 再跑一次檢查，fetch 或重跑失敗就問人類；沒有採用宣告時不必 fetch。
    - 不合法的路徑：空、前後空白、看不見的字元、行尾註解（空白後接 `#`）、絕對路徑、磁碟代號、`\`、萬用字元、空的或
      `.`、`..` 段、`#` 開頭的段、`.git`、`.toukadev` 或快取名稱段，或在被清的工作資料夾裡沒被 git 忽略（check-ignore）。
    - 等於宣告路徑或在它底下才算，逐段比對（`dist` 不涵蓋 `dist-data`），Windows 上只把 ASCII 轉小寫、`\` 當成 `/`。
      列出的路徑即使整份不採用，也取消快取豁免：連結、junction、reparse point、空白 `.git` 標記、巢狀與 bare repo
      一律擋。快取名單、其他條件、刪法（`git worktree remove`，不加 `--force`）與唯讀不變；原本會通過的照樣通過。
    - 對抗式複審（第 12 項）：2 位唯讀審查者，同一模型的新上下文、只看本 repo，題目是 ①「會不會刪到不該刪的」、②「原本
      能清的還能不能清」。第 1 輪：① 1 MEDIUM（看不見的文字被當成宣告）＋4 LOW；② 1 MEDIUM（缺測試）＋4 LOW。技術主管
      裁定修 9 點、都往擋下的方向，人類同意修法並要原審查者複驗（`6d614f0`）；同類的「看不見的宣告」第二次出現後改成
      白名單（`bab4f20`）。修正後第 2 輪複驗兩位都沒過，同一類「畫面看不到的宣告」問題出現第三次；人類改選把宣告放在
      純文字檔，Markdown／HTML 的判斷整段拿掉（`9c32357`）。
    - 第 3 輪複驗：兩位都 PASS_WITH_NOTES，沒有擋路的問題；相對 dev 基準，除了人類核准的宣告機制本身，沒有放寬。剩下的
      LOW 由技術主管驗收、修在 `1fa0333`（上面的一般檔、空行不含空白、看不見的字元與行尾註解、只在靠宣告放行時才印）。
14. **D14 縮短描述網頁畫面的段落**（第 14 項；`c43d724`）：progress-record「網頁會顯示什麼」32 行縮成 12 行；保留
    「看到警告就修正紀錄」「改用同一個時間來源」與測試核對的時間門檻。
15. **D15 刪除快捷指令 `commands/`**（第 13 項，人類確認其他電腦與專案都沒裝；`3f55226`）：6 個檔，和 ADR-040 刪的
    `hooks/` 同類。同步改根 README（安裝說明、目錄樹、「原生 `/quick`」那句）、dev-workflow SKILL 的 `/quick` 兩行、審核
    協議 §2.2（「`/quick` 沒有 DEV-A」改「文件快速路徑沒有 DEV-A」，規則不變）、四份 glossary 與 SSOT 導航（`/quick` 改列
    為舊稱）；拿掉只保護 `commands/` 的守衛條目（F8、F11、F17），F11 的 glossary 那句同步改寫，測試同 commit；前後各跑
    一次 `git grep`，殘留只能是 ADR 歷史與改寫後的舊稱句（DEV-A 裁定）。

## 不採用與延後

- 不採用第 16 項（路徑含 `.toukadev` 讓某個工具誤報）：只有一個工具受影響，工作資料夾位置又受清理前檢查限制；建議
  那個專案修工具設定，修好前遇到就停下問人類（人類當次決定，不成為常設例外）。
- 不採用第 1 項討論稿 D 的六項（定時自動收集與修正、每天排程維護技能、只有不可逆的事才先問、競爭原型、預設用其他
  公司的模型驗證、試用期沉默就退回）：會悄悄削弱審核點、多花額度，或把沉默當同意。
- 延後第 15 項（範例專案）：本任務不刪，之後另開任務刪。
- 推翻 ADR-037 D3 的理由：D3 當時只發生一次，約定其他專案也發生時再評估 `CACHEDIR.TAG`。這次是同一個專案再發生、
  規模大得多；`CACHEDIR.TAG` 也不合用：`*.tsbuildinfo` 是單一檔案放不了標記，`dist/` 與產生的原始碼是建置輸出不是
  快取。名稱名單猜不完，改由專案在預設分支宣告、人類在一頁計畫核准。
